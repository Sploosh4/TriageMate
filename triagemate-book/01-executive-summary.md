# TriageMate Book — Chapter 1: Executive Summary

Welcome to the TriageMate Book. This is not a dry technical document. Think of this as a guided audio deep dive — the kind of conversation you would have with a senior colleague over coffee, where they walk you through a system from first principles. By the time we finish, you will understand not just what TriageMate does, but why it exists, how it evolved, and where it is going.

Let us start with a problem. Picture a security operations centre analyst in the Western Australian government. Every week, a fresh batch of vulnerability scan results lands on their desk. Hundreds of CVEs — sometimes thousands. Each one is a potential hole in a system somewhere across the state's public sector infrastructure. The analyst needs to figure out which of these vulnerabilities actually matter. Which ones are being exploited in the wild? Which ones affect critical assets? Which ones can wait until next month?

This is the core pain that TriageMate exists to solve. Vulnerability overload leads to prioritisation paralysis. When everything looks urgent, nothing is. Analysts drown in scanner output. They spend more time sorting than fixing. The human brain is simply not built to rank five hundred items by risk level, consistently and without bias, week after week. Tools exist, but they tend to be either too simplistic — a CVSS score alone tells you almost nothing about real-world risk — or too complex, requiring days of configuration before they produce a single useful result. TriageMate was built to sit in the middle: a fully automated pipeline that ingests raw vulnerability data and outputs a ranked, scored, and actionable queue.

Here is the elevator pitch. TriageMate is a vulnerability triage pipeline purpose-built for Western Australian government SOC analysts. You feed it a raw vulnerability, and it pushes that vulnerability through four analysis tiers. By the time it comes out the other end, it has a priority score from zero to one hundred, it has been classified into one of four risk bands, and it has been assigned to the right queue based on the mission criticality of the affected asset. The analyst opens their dashboard and sees a clean, sorted list. They start at the top and work down. No guesswork. No frantic cross-referencing of EPSS and CISA KEV and ExploitDB and asset registers. The machine does the cross-referencing. The human does the judgement.

Let us talk about the architecture. At a high level, the system works like a factory assembly line running in reverse. Instead of raw materials coming in and finished goods going out, raw vulnerabilities come in and finished intelligence goes out. The line has four stations, and we call them tiers. The first station is Pre-Tier — mission classification. Before anything else happens, the system figures out what kind of asset this vulnerability lives on. Is it a corporate workstation? A critical police database server? A health system endpoint? An IoT device in a regional water treatment plant? Each of these gets a different mission category, and that category feeds directly into scoring. A critical vulnerability on a non-critical asset is still a problem, but it is a lower priority than the same vulnerability on a life-safety system.

The second station is Tier 0 — deterministic rules. This is the fastest path in the pipeline. The system applies a set of hard-coded rules that capture the no-brainer cases. Is this CVE in CISA's Known Exploited Vulnerabilities catalogue? That is an immediate score boost. Is there a published Metasploit module or an ExploitDB proof-of-concept? Another boost. Is the EPSS score above a certain threshold? Yes, boost. Tier 0 handles the cases where the answer is clear and the evidence is unambiguous. These rules run in milliseconds.

The third station is Tier 1 — machine learning. Here we bring in an XGBoost model trained on historical vulnerability data. The model has eight hundred decision trees behind it, and it has been trained to answer one specific question: given everything we know about this vulnerability and its asset context, what is the probability that it will be exploited in the next thirty days? The model looks at features like CVSS subscores, EPSS probability, whether there is exploit code available, the age of the vulnerability, the complexity of the attack vector, the mission type of the asset, and dozens of other signals. It produces an exploitation probability between zero and one. On evaluation, this model achieves a ROC-AUC between 0.9677 and 0.9946 across different mission categories. That is extremely strong discrimination — the model is very good at telling apart the vulnerabilities that will be exploited from the ones that will not.

The fourth station is Tier 2 — a cloud large language model. This is the slowest tier, but also the most flexible. When the pipeline encounters a vulnerability that the deterministic rules and the ML model are uncertain about, it sends the full context to a frontier LLM — OpenAI, Anthropic, or Together, depending on configuration. The LLM is prompted with a structured analysis request. It returns a reasoned assessment, a suggested priority override, and optionally a natural language summary that gets surfaced to the analyst. Tier 2 catches edge cases that the rules and the model were never trained on. It is the safety net.

After all four tiers have run, the outputs feed into the scoring engine. The scoring engine computes a final score from six dimensions. CVSS severity contributes up to forty points. EPSS probability contributes up to twenty points. Asset criticality contributes up to twenty points. Exposure and access complexity contributes up to fifteen points. Patch availability contributes up to five points. And the ML exploitation probability contributes up to ten points. The final score maps to four risk bands. Zero to twenty-five is Low. Twenty-six to fifty is Medium. Fifty-one to seventy-five is Critical. Seventy-six to one hundred is Very Critical. The analysts sees these as colour-coded entries in their queue — green, amber, red, and deep red.

Now let us rewind and talk about how we got here. TriageMate did not start as a four-tier pipeline with machine learning models and vector databases. It started as a single-file HTML demo. The very first version was a static page with hard-coded vulnerability data styled to look like a triage dashboard. It was a proof of concept — something to wave in front of analysts and say, "Does this look useful?" They said yes. So we started building.

The project evolved through nine sprints over several months. Each sprint added a layer of capability. Sprint one established the basic data model and the first version of the deterministic Tier 0 rules. Sprint two brought in the first XGBoost model and the early scoring engine. Sprint three introduced the frontend SPA and the queue view. Sprint four added the case detail view and basic filtering. Sprint five built out the ingestion pipeline and the first database migrations. Sprint six added the Pre-Tier mission classification using hostname-based dictionary lookups. Sprint seven introduced Tier 2 LLM integration and the review queue for analyst feedback. Sprint eight hardened the system with authentication, rate limiting, Docker support, and test suite expansion. Sprint nine — the current sprint — completed the data corpus, migrated to full PostgreSQL compatibility, added the drift dashboard, and refined the scoring engine into its final form.

As of Sprint nine, in July 2026, TriageMate is a production-capable MVP. Let me run through what is implemented. The data corpus is comprehensive. It includes 186,102 CVE records from NVD, 344,852 EPSS probability scores, 1,631 entries from the CISA Known Exploited Vulnerabilities catalogue, 47,089 ExploitDB entries mapping exploits to CVEs, and a vendor index covering 17,100 entries. All of this data is loaded into the system and queryable. The four-tier pipeline is fully operational. You can feed it a vulnerability and watch it flow through Pre-Tier mission classification, Tier 0 deterministic rules, Tier 1 XGBoost prediction, and Tier 2 LLM analysis, with the results aggregated into the scoring engine.

The frontend is a single-page application built with static HTML and JavaScript — no build step required. It has four screens. The Queue screen shows the prioritised list of vulnerabilities with their scores, risk bands, and key indicators. The Case screen provides a detailed view of a single vulnerability, showing the outputs of each tier, the scoring breakdown, and the raw evidence. The Review Queue is where analysts provide feedback — they can agree or disagree with the system's priority, flag false positives, and add notes. The Drift Dashboard tracks model performance over time, showing how well the ML predictions are matching real-world outcomes, and alerts when the distribution of scores starts to shift in unexpected ways.

The backend is built on FastAPI with a choice of SQLite for development or PostgreSQL for production. Authentication uses JWT tokens, optional but recommended. Rate limiting uses a token bucket approach — thirty ingest requests per minute, ten for the demo endpoint, two for the clear endpoint. The entire system runs in Docker via a docker-compose setup. There are thirty-seven automated tests and five Alembic database migrations covering the schema evolution.

The ML subsystem is worth a closer look. The primary Tier 1 model is an XGBoost classifier with eight hundred trees. It was trained on a dataset of historical CVEs with known exploitation outcomes. The performance varies by mission category. For corporate assets, the ROC-AUC is 0.9946. For health assets, it is 0.9677. For critical infrastructure, it is 0.9789. These are strong numbers. The model is not guessing — it is discriminating with high confidence. In addition to the XGBoost model, there is a Pre-Tier Random Forest model that handles mission classification using a MultiOutputClassifier with one hundred and fifty trees. This model is currently inactive in the pipeline — the Pre-Tier stage still uses a hostname-based dictionary lookup — but it has been trained on synthetic data with seven mission types and three wellbeing categories and is ready for activation.

There is also an EPSS substitution model. This is a v3 XGBRegressor trained on the full corpus of 344,852 real EPSS scores. It was created because the EPSS API is rate-limited, and the system needs to be able to estimate EPSS scores for CVEs it cannot fetch in real time. The substitution model takes a CVE's CVSS features and predicts its EPSS score with reasonable accuracy. This allows the pipeline to produce a score even when the EPSS API is unavailable, and the substitution model itself was trained on real EPSS data, so its predictions reflect actual distributional patterns.

The vector search system uses Sentence-BERT with the all-MiniLM-L6-v2 model generating three-hundred-and-eighty-four-dimensional embeddings, stored in a LanceDB vector database. This powers similarity search — finding CVEs that are semantically similar to a given vulnerability, which is useful for the case detail view and for the drift dashboard's cluster analysis.

Background processes keep the system current. A daily low-severity re-check job scans the last seven days of low-severity vulnerabilities to see if any conditions have changed — maybe a new exploit was published, or the EPSS score jumped. A seven-point-five percent audit sampling rate sends a random subset of vulnerabilities through Tier 2 LLM review even when the deterministic and ML scores are confident, providing a continuous check on system performance.

Now let us talk about what is planned. SprINT NEXT — the next development cycle — has five major deliverables. First, the XGBoost model will be retrained on a new dataset called training_data_v2.npz. This dataset contains 144,000 records with 67 features, and crucially, it was generated from real data distributions rather than synthetic assumptions. The current model was trained on synthetic data because real exploitation outcome data is scarce. The v2 dataset incorporates findings from the actual data exploration — the real distributions of CVSS scores, EPSS probabilities, asset types, and exploitation timelines. The retrained model will be more realistic and more robust.

Second, the Pre-Tier Random Forest model will be activated, replacing the hostname-based dictionary lookup for mission classification. The dictionary approach works but is brittle — it only covers hostnames it has seen before. The RF model can classify any asset based on its features, even if the exact hostname has never been encountered. This will make the pipeline more general and reduce maintenance burden.

Third, the EPSS substitution model will be retrained on the full set of 344,852 real EPSS scores. The current model was trained on a smaller sample. The retrained model will capture more nuance in the distribution and produce better estimates.

Fourth, rate limiting will be made configurable through environment variables instead of being hard-coded. This is a production-readiness concern — different deployments need different rate limits, and operators should be able to tune these without changing source code.

Fifth, the test suite will be hardened and operational guards will be added. The current thirty-seven tests cover the core logic, but the production system needs additional tests for integration scenarios, error handling paths, and performance guardrails. Operational guards include things like circuit breakers for LLM API calls, fallback behaviour when the EPSS API is unreachable, and alerting when the pipeline produces anomalous results.

Beyond Sprint NEXT, the roadmap is guided by a long-term vision. Picture TriageMate as a fully productionised SOC tool running in the Western Australian government security operations centre. The automated triage pipeline runs continuously. Scanners feed vulnerabilities into the ingestion endpoint around the clock. The four-tier pipeline processes each one, assign scores, routes cases to queues, and surfaces the highest-priority items to analysts. The average time from ingestion to queued and scored is measured in seconds. The analyst's morning routine is not sorting through a firehose of alerts — it is reviewing the top ten items in their queue, each one already enriched with all the context they need.

The queue dashboard becomes the central nervous system of vulnerability operations. Analysts can filter by mission category, risk band, date range, and CVE attributes. They can drill into individual cases to see the reasoning trail — which tier produced which signal, what evidence was considered, what the LLM recommended. The review queue becomes a feedback loop. When an analyst disagrees with a score, that feedback is logged. Over time, the pattern of human overrides becomes a dataset in itself, used to retrain the ML models and tune the deterministic rules. The system learns from its mistakes.

The drift dashboard gives operations managers visibility into model health. They can see if the distribution of ML scores has shifted in the last week, if the proportion of Very Critical vulnerabilities is suddenly rising, if the LLM Tier 2 override rate is increasing. These are early warning signals that something has changed in the threat landscape or the asset environment. The dashboard turns model monitoring from a manual inspection task into an automated alerting system.

The data corpus grows with every vulnerability processed. The vector database accumulates embeddings, enabling richer similarity search and cluster analysis. The EPSS substitution model improves as more real EPSS data becomes available. The XGBoost model gets retrained quarterly with fresh outcome data from the review queue feedback. Each retraining cycle improves accuracy and reduces the need for human intervention.

There is a human review at every critical decision point, but the volume of human work shrinks over time. The goal is not to replace the analyst. The goal is to remove the noise so the analyst can focus on the signal. A triage pipeline that handles eighty percent of cases automatically — scoring them, categorising them, routing them — and surfaces only the remaining twenty percent for human judgement. That is the sweet spot. That is what TriageMate is designed to achieve.

From a technical standpoint, the system is deliberately conservative in its dependencies. The backend is pure Python with FastAPI, SQLAlchemy, and standard data science libraries. The frontend is vanilla HTML, CSS, and JavaScript — no React, no Vue, no build pipeline. This is a deliberate choice. SOC tools need to be maintainable by people who are not full-time web developers. They need to run on air-gapped networks where pulling npm packages from the internet is not an option. They need to be auditable and understandable. A system that fits in a single codebase with minimal external dependencies is a system that can be deployed, debugged, and extended by a small team. That is the philosophy.

Let me summarise where we are. TriageMate began as a single HTML file. Nine sprints later, it is a complete vulnerability triage pipeline with four analysis tiers, a scoring engine, a frontend dashboard suite, ML models with strong performance metrics, a comprehensive data corpus, authentication, rate limiting, Docker deployment, and a growing test suite. The architecture is clean — FastAPI backend, SQLite or PostgreSQL database, static frontend, background workers for periodic tasks. The scoring model is transparent — six dimensions, explicit weights, four risk bands. The ML models are performing well and are scheduled for retraining on real data. The planned work for Sprint NEXT will close the gap between MVP and production system.

What comes after that is the vision. A SOC tool that runs continuously, triages automatically, learns from feedback, and lets analysts do what analysts do best — make informed judgements about the threats that matter. TriageMate is not a magic bullet. It is a force multiplier. It takes the overwhelming flood of vulnerability data and turns it into a manageable, prioritised, actionable stream. That is the whole point.
