# TriageMate Book — Chapter 12: The Frontend SPA

In the last chapter we went deep into the backend pipeline — the four tiers, the scoring engine, the data models. But a pipeline that nobody can see might as well not exist. The frontend is where the rubber meets the road. It is what the analyst looks at all day. It is the interface between the machine's judgement and the human's decision. Get this wrong and none of the backend sophistication matters.

TriageMate's frontend is a single-page application built with vanilla JavaScript, HTML, and CSS. No React. No Vue. No Svelte. No build step. No npm dependencies. This was a deliberate architectural decision. SOC tools often run on air-gapped networks where you cannot just `npm install` your way to a working UI. The frontend needs to be deployable by copying a directory of files onto a web server. FastAPI serves `index.html` and the static JS and CSS files from a `frontend/` directory, and that is the entire deployment story for the UI. Nine files. No bundler. No tree-shaking. No transpilation. It works.

Let us talk about the file structure because it maps directly to how the application is organised. The entry point is `frontend/index.html` — one hundred and ninety-eight lines of declarative markup. The styles live in `frontend/css/triagemate.css` — sixteen hundred and sixty-seven lines of carefully crafted CSS. The JavaScript is split across `frontend/js/api.js` at one hundred and eight lines, `frontend/js/app.js` at two hundred and seventy-four lines, and seven component files under `frontend/js/components/` totalling roughly eleven hundred lines. The total frontend footprint is just over three thousand lines. That is smaller than a single React component in most enterprise SPAs.

The SPA has four screens. Queue View is the default — the screen the analyst lands on when they open TriageMate. It is a sortable table of all active vulnerabilities. Columns include Vulnerability ID, Hostname, Priority Score, Risk Band, Tier, Detection Reason, WA Compliance, and Since — that is days since creation. Every column header is clickable. Click once for ascending sort, click again for descending. The sort state is maintained in a global `sortState` object with `column` and `direction` properties, and the default sort is by priority score descending — highest risk first. The detection reason column has a nice touch: it strips the tier prefix before display, so instead of seeing "SLM Tier: CVE-2024-1234 allows remote code execution" the analyst sees just "CVE-2024-1234 allows remote code execution". The tier information is still available in a dedicated column.

Above the table there are four metric boxes. Critical Actions counts vulnerabilities with a risk band of Very Critical. Low Confidence counts SLM Tier entries plus ML Tier entries where the model confidence is below eighty-five percent. Exposed counts internet-facing assets. Needs Human Validation counts SLM Tier entries — these are the ones that need an analyst to look at them. Each metric box has a coloured left accent bar — red for critical, amber for low confidence, orange for exposed, blue for human validation. The boxes are clickable. Click one and the queue filters to show only matching rows. A box-shadow ring appears on the active filter. Click it again to clear. The boxes also update their subtitle text dynamically — if the count drops to zero, the subtitle changes from "Require immediate attention" to "No critical items in queue". Small detail, but it makes the empty state feel intentional rather than broken.

The top bar has a search input that filters by vulnerability ID or hostname in real time, a tier filter dropdown with four options — All Tiers, Deterministic, ML Tier, SLM Tier — and two tab buttons for Review Queue and Drift Dashboard. There is also a demo toggle button that appears when the backend has demo mode enabled. The search input has a nice focus animation — it expands from two hundred and forty pixels to three hundred pixels on focus, giving the analyst more room to type.

Responsive behaviour is handled entirely in CSS with media queries. At nine hundred pixels, the compliance and since columns collapse via `visibility: collapse`, the metric boxes wrap to two per row, and the case view panels stack vertically. At six hundred pixels, the queue table transforms into a card layout — the `<thead>` disappears, each row becomes a bordered card, and every `<td>` uses `::before` with `content: attr(data-label)` to show the column label alongside the value. This is a pure CSS card transformation with no JavaScript involvement. The top bar also stacks at this breakpoint, wrapping the search input and filter below the app name.

When the analyst clicks a queue row, the application navigates to the Case View. This is the most complex screen in the SPA — four panels in a scrollable view, designed to give the analyst everything they need to make a triage decision without scrolling back and forth.

Panel 1 is the narrative summary. It displays auto-generated paragraphs describing the vulnerability, drawn from the LLM output when available or from the deterministic analysis when not. Below the summary, mission prevalence tags appear as coloured pills — these indicate the mission types affected by this vulnerability across the estate. Then the MITRE ATT&CK technique badges, each showing the technique ID and name. The badges have a hover lift animation — `translateY(-1px)` on hover — that gives them a tactile feel despite being purely CSS. If the vulnerability had an SLM text conflict — meaning the small language model produced a summary that contradicted the deterministic analysis — Panel 1 gets a yellow background with a three-pixel amber left border. A text conflict notice appears as a highlighted box below the MITRE badges.

Panel 2 is the accordion container. Three accordions, each with a header button and a collapsible body. Scanner Output shows the raw scan result in a dark-background code block using JetBrains Mono font. Weakness Logic Template shows the YAML weakness template with syntax highlighting — keys in blue, strings in green, booleans in purple, numbers in yellow — applied by a regex-based `highlightYaml` function that runs entirely in the browser. WASOC Advisory Reference shows the advisory quote in a serif italic style with a left border, giving it the visual character of a blockquote from a printed document. The accordions use `max-height` transitions for smooth opening and closing — no JavaScript animation, just CSS `transition: max-height 250ms ease`. The scanner accordion is open by default; the others start closed.

Panel 3 has two sections. On the left, an investigation notes textarea that is resizable. The analyst can type notes and save them with the Save Notes button or by pressing Ctrl+S or Cmd+S. The save triggers a `PATCH /api/case/{id}/notes` request, and a status indicator shows "Saving...", then a green checkmark on success or a red cross on failure. On the right side of Panel 3, there is a score gauge bar — twenty pixels high, using a four-colour linear-gradient background at twenty percent opacity as a reference zone, with the actual score fill at full opacity. The gradient transitions from green at zero to yellow at twenty-five to orange at fifty to red at seventy-five. Below the gauge, the numeric score and the risk band label are displayed, with the band name coloured to match the risk level. Below the gauge, if the system has substituted an EPSS score — because the real EPSS API was unavailable or rate-limited — a greyed-out block with a purple left accent appears. It shows the original EPSS value, the substituted value, the model confidence, and the reason for the substitution.

Panel 4 is split into two halves. The left half shows the Scoring Weight Itemisation — six dimension breakdown rows, each showing the dimension name, the awarded points out of the maximum, the justification text, and a substitution badge if that dimension used an internal metric instead of a real data source. If the enrichment data is stale — meaning the NVD data is older than twenty-four hours — a "Enrichment Stale" badge appears next to the section title. The right half shows the Asset Registry Entry — key-value rows for data classification, network zone, operating system, asset owners, interface type, and any other registry fields the asset database knows about.

Navigation between screens is handled by the `navigateToScreen` function in `app.js`. It hides all screens, shows the target, and updates the `appState.screen` property. The back button and the Escape key both return the analyst to the Queue View. The Escape handler is guarded to only fire when the current screen is `case`, so it does not interfere with other contexts.

The Review Queue is a dedicated screen for cases that have been flagged for human review. It opens as a table with columns for Vulnerability ID, Hostname, Score, Risk Band, Tier, Review Status, and Conflict. Each row is clickable. Clicking a row expands it to show the full case detail — reusing the same rendering approach as the Case View but embedded in the review context. Below the case detail, a review form appears with decision buttons: Confirm Score or Override Score. These toggle a selected state with green and orange borders respectively. If the analyst clicks Override, a score slider and band selector slide into view. There is a notes textarea, an analyst name field, and a Submit button that sends a `POST /api/case/{id}/review` with the decision, notes, analyst name, and optionally the override score and band. The review queue has its own state object — `reviewState` — that tracks the expanded row ID, the loaded case data, and whether a detail load is in progress. After submission, the queue refreshes automatically.

The Drift Dashboard is the fourth screen. It displays model drift metrics fetched from `GET /api/drift` using CSS-only charts — no charting library. Four panels in a two-by-two grid at desktop, collapsing to a single column at nine hundred pixels. Panel 1 is a score trend sparkline: vertical bars in a flex container, heights proportional to score, coloured by threshold — red above seventy-five, orange above fifty, yellow above twenty-five, green at or below twenty-five. Panel 2 is the tier routing visualisation: a segmented horizontal bar showing the proportion of auto-routed versus escalated cases, with a legend below. Panel 3 is the risk band distribution: four rows, each with a label, a proportional fill bar, and a count. Panel 4 is a feature drift table showing feature names and their current values. All of this is rendered by `driftDashboard.js` in under one hundred lines.

Now let us talk about the JavaScript architecture, because it is an object lesson in keeping things simple. There are two main files plus seven components. `api.js` has one job — talking to the backend. It defines a single private helper called `_authFetch` that wraps the standard `fetch` API. When a token is available, it attaches a Bearer authorization header. When the server returns a 401, it attempts a token refresh by calling `refreshToken()`, retries the original request once, and if the refresh also fails, it calls `logout()` which clears localStorage and reloads the page. All public API functions — `fetchQueue()`, `fetchCase()`, `fetchMetrics()`, `saveNotes()`, `fetchReviewQueue()`, `flagForReview()`, `submitCaseReview()`, `fetchCaseHistory()`, `fetchDriftMetrics()` — use `_authFetch` internally. The API layer is a hundred and eight lines and it handles authentication transparently for every endpoint.

`app.js` is the application controller. It defines `appState` — a singleton object with `screen`, `currentRowId`, `filter`, `queueData`, `currentCaseData`, `activeMetricFilter`, `searchQuery`, and `accordionOpen` properties. The `init()` function is called on `DOMContentLoaded`. It first calls `initAuth()` to check whether authentication is required — if it is and the user is not logged in, the login modal appears and `init()` stops. Then it checks the health endpoint for demo mode status and shows a watermark banner if active. Finally, it fetches queue and metrics data in parallel via `Promise.all`, renders the queue table and metric boxes, and wires up all event listeners.

The `wireEventListeners()` function is a single monolithic setup that registers handlers for search input, filter change, column sort clicks, queue row clicks, queue row keyboard events, back button, accordion toggles, metric box clicks, metric box keyboard events, notes save button, Ctrl+S keyboard shortcut, Escape keyboard shortcut, review tab, drift tab, review back button, drift back button, and demo controls. Event delegation is used extensively — the queue table body gets a single click handler that checks `e.target.closest('tr[data-row-id]')` instead of attaching a handler to every row. The accordion container uses the same pattern. This keeps the memory footprint small and avoids the need to reattach listeners when the DOM changes.

The component files are loaded in dependency order via `<script>` tags in `index.html`: `api.js` first, then `queue.js`, `caseView.js`, `metricBoxes.js`, `demoControls.js`, `auth.js`, `reviewQueue.js`, `driftDashboard.js`, and finally `app.js`. Each component file declares global functions that `app.js` calls. There are no modules, no imports, no bundler steps. This is pre-ESM JavaScript, and it works fine for an application of this size.

`queue.js` provides `renderQueue()`, `sortRows()`, `filterRows()`, `searchMatch()`, `getRiskColour()`, `getTierBadgeClass()`, `metricFilterMatch()`, and `updateSortArrows()`. The risk colour function maps scores to colours: zero to twenty-five is green, twenty-six to fifty is amber, fifty-one to seventy-five is orange, seventy-six to one hundred is red. The tier badge class returns CSS class names that produce different coloured pill badges — green for deterministic, purple for ML, amber for SLM. The `metricFilterMatch` function encodes the four metric box filter logics: critical checks for Very Critical risk band, human-val checks for SLM Tier, low-conf checks for SLM Tier or ML Tier with confidence below 0.85, exposed checks for internet-facing interface type.

`caseView.js` provides `renderCase()` and `highlightYaml()`. The YAML highlighting is a series of regex replacements that wrap keys, strings, booleans, and numbers in span tags with CSS classes. It runs on the escaped HTML version of the YAML template, so it handles special characters safely. The `renderCase` function populates all four panels from a `caseResponse` object. It handles the substitution block visibility, the stale enrichment badge, the text conflict styling, and the accordion default open state.

`metricBoxes.js` exports a single function `updateMetricBoxes()` that recomputes the four counts from the current queue data. It also handles the empty state subtitles and ARIA labels for accessibility.

`auth.js` provides the full authentication flow. `initAuth()` is called by `app.js` at startup. It first pings the health endpoint to check if `auth_required` is true. If auth is disabled, it returns immediately. If auth is required and the user has valid stored tokens, it returns. If auth is required and the user is not authenticated, it wires up the login UI and shows the modal overlay. The login modal has username and password fields with keyboard flow — Enter in the username field advances focus to the password field, Enter in the password field triggers login. After successful login, the modal hides and `init()` is called again to load the queue data with the new token. Tokens are stored in localStorage under the key `triagemate_auth`, with the access token, refresh token, and an expiry timestamp set to twenty-five minutes — slightly under the thirty-minute server expiry to give a buffer. The `refreshToken` function calls `POST /api/auth/refresh` and updates the stored tokens. The `logout` function clears storage and reloads the page.

`reviewQueue.js` is the largest component at three hundred lines. It manages its own `reviewState` — rows, expanded ID, case data, and a loading flag. `initReviewQueue()` fetches the review queue data from `/api/review/queue` and renders the table. `loadReviewCaseDetail()` fetches the full case data for the expanded row and re-renders with the detail panel. `submitReview()` validates that a decision is selected and an analyst name is entered, then sends the review payload to the backend. After a successful submission, it waits eight hundred milliseconds, then re-initialises the review queue and refreshes the main queue. The `renderReviewDetail()` function builds the HTML for the expanded case view — summary, accordions, scoring weights, review form — entirely as string concatenation. No templates, no JSX, no client-side rendering library. Just JavaScript, backticks, and HTML strings.

`driftDashboard.js` is the simplest component at ninety-six lines. `initDriftDashboard()` fetches drift data from `/api/drift` and calls `renderDriftDashboard()`. The render function checks if there are audited cases — if not, it shows an empty state message. Otherwise it builds the four panels. The sparkline bars are `<div>` elements with inline `height` and `background` styles. The tier routing bar uses percentage widths calculated from the auto and escalated counts. The risk band distribution uses proportional fill widths relative to the maximum count. All colours are hard-coded in the JavaScript — no colour scale library, no charting dependency.

Let us talk about the authentication decision. Auth is optional. When the `TRIAGEMATE_ADMIN_USER` environment variable is set on the backend, the health endpoint returns `auth_required: true` and the frontend shows the login modal. When it is not set, the modal never appears and the frontend works without authentication. This is critical for development, demos, and air-gapped deployments where authentication might be handled by a reverse proxy instead. The frontend detects which mode it is in at startup and adapts behaviour accordingly.

The keyboard shortcuts are lightweight but effective. Ctrl+S or Cmd+S saves notes on the Case screen. Escape returns to the Queue View from the Case screen. Enter or Space opens a case from a focused queue row. Enter in the username field of the login modal advances focus to the password field. Enter in the password field triggers login. These shortcuts are wired in `app.js` using `document.addEventListener('keydown', ...)`, guarded by the current screen state.

The CSS is worth a closer look because it carries a lot of the application's weight. The queue table is a standard HTML table with collapsed borders, uppercase headers, and hover highlights. The sort arrows are Unicode characters — up and down triangles — toggled by `updateSortArrows()` based on the current sort state. The compliance badges are pill-shaped with coloured borders matching the category — grey for Category 2, orange for Category 3, red for Category 4. The tier badges use the same pill pattern with green, purple, and amber colour schemes. The entire responsive behaviour at six hundred pixels — the card layout transformation — is pure CSS using `display: block` on the table elements and `::before` pseudo-elements for the column labels. No JavaScript detects the viewport width. No ResizeObserver. Just media queries.

The scrollbar is custom-styled for WebKit browsers — six pixels wide, rounded thumb, transparent track. The focus ring is consistent across interactive elements using a CSS custom property `--focus-ring` that applies a three-pixel blue box-shadow with transparency. The metric boxes use a `::before` pseudo-element for the left accent bar and a subtle linear-gradient background that fades from a tinted colour on the left to white. The active filter state adds a two-pixel box-shadow ring in the accent colour.

The substitution block in the case view is a fascinating piece of UX. It is positioned with `position: relative` and the label is absolutely positioned in the top-right corner. When a substitution has occurred, the entire block gets `opacity: 0.4` — this makes it visually recede so the analyst's eye is drawn to the actual score gauge rather than the substitution note. The purple left accent uses `--substitution-accent: #7C3AED` — the same purple that appears in the ML Tier badge, creating a visual association between the ML system and its substitution behaviour.

The gauge bar is a two-layer construct. The background layer is the reference zone — `opacity: 0.2` showing the full four-colour gradient so the analyst can see where the thresholds are. The fill layer is a child `<div>` with `position: absolute` and `width` set dynamically from the score value, at `opacity: 1`. The fill itself uses the same gradient, so as the fill expands it reveals the correct colour band for the current score. This is purely decorative but it gives an immediate visual sense of where the score falls in the risk spectrum.

Now let us talk about what is planned. The frontend is essentially complete for the MVP scope. Every screen is built, every interaction is wired, every API endpoint has a corresponding frontend function. There are three post-MVP enhancements on the roadmap. Dark mode is the most requested feature from the analyst previews — a CSS custom property swap that would allow the UI to switch to a dark colour scheme. It is technically straightforward but requires auditing every colour in the stylesheet for contrast and readability in both modes. The second enhancement is real-time updates via WebSocket. Currently the analyst must refresh or navigate to see new vulnerabilities that have been ingested since they opened the queue. A WebSocket connection would allow the backend to push new row notifications, and the frontend could insert them into the queue without a full re-fetch. The third enhancement is notification badges — showing a count of new items or pending reviews on the browser tab and on the Review Queue button.

There is also the demo mode layer. When the backend is running in demo mode, a sticky watermark banner appears at the top of the screen reading "FICTITIOUS DATA — FOR DEMONSTRATION ONLY — NOT REAL VULNERABILITIES" in amber. The demo mode toggle button in the top bar reveals a Demo Data Generator panel with a scenario picker, wave size selector, generate button, and clear button. The panel is styled with a dark background and teal accent colours to visually distinguish it from the production UI. This was built for live demonstrations where the operator needs to generate realistic-looking data on the fly.

Let me summarise the frontend philosophy in one sentence: zero dependencies, maximum readability, full functionality. The entire frontend is three thousand lines of vanilla code that anyone comfortable with HTML, CSS, and JavaScript can understand and modify. There is no build step, no transpilation, no package manager, no node_modules directory. You can deploy it by copying files to a static directory behind FastAPI. You can debug it by opening the browser's developer tools and setting breakpoints in the actual source files you wrote. You can extend it by adding a new component file, loading it with a `<script>` tag, and calling its exported function from `app.js`. This is not the trendy way to build web applications in 2026. It is the durable way.
