# Chapter 4: The Ingest Pipeline — From Scanner Output to Scored Queue Entry

Every vulnerability in TriageMate starts life as raw scanner output — a Nessus JSON export, a Tenable webhook payload, or a manual API call. By the time it appears in the queue, it has passed through fourteen processing steps spanning asset classification, threat intelligence enrichment, deterministic rules, gradient-boosted machine learning, a semantic vector search, and — for the hardest cases — a cloud-hosted language model that debates itself. This chapter walks that entire journey.

The pipeline lives in `backend/routers/ingest.py`, with logic delegated to `backend/ingest_helpers.py`, the four pipeline stages in `backend/pipeline/`, the scoring engine in `backend/scoring.py`, the CWE classifier in `backend/ingest_cwe.py`, and integration modules under `backend/integrations/`. There are three ingest entry points. `POST /api/ingest` accepts a single `IngestRequest` and runs the full fourteen-step pipeline. `POST /api/ingest/batch` accepts a list and calls the single-ingest endpoint for each. `POST /api/ingest/tenable` accepts raw Tenable.io JSON — it auto-detects webhook envelopes, bare findings, or batch lists, parses them through `parse_tenable_webhook` or `parse_tenable_batch` in `backend/integrations/tenable.py`, and routes into the pipeline. A demo generator at `POST /api/demo/generate`, gated behind `DEMO_MODE=true`, produces findings from pre-built scenarios or random waves, injects enrichment, and feeds them through the batch pipeline.

## Step 1 — Pre-Tier: Mission Tag Prediction

The very first thing the pipeline does, before it even looks at the CVE identifier, is classify the asset. It calls `pre_tier.predict_mission_tags(hostname, ip)` from `backend/pipeline/pre_tier.py`. This function has three layers of resolution. First, it checks the `KNOWN_TAGS` dictionary, a hardcoded mapping of thirty-one Western Australian Government hostname patterns to their mission prevalence (Core, Support, or Peripheral) and public well-being impact (Severe, Moderate, or Minimal), each with an associated confidence score. These thirty-one entries cover the full set of demo hosts from the seed data — health data exchange servers, transport gateway appliances, education print servers, police knowledge management wikis, and more. If the hostname matches exactly, the hardcoded tags with their original confidence scores (typically 0.85 to 0.96) are returned immediately.

If the hostname is not in the known set, the function attempts to load and run a trained machine learning model — a `MultiOutputClassifier` wrapping a `RandomForestClassifier` with one hundred and fifty trees, stored in `backend/ml/pre_tier_model.pkl`. The model was trained on feature vectors extracted from those same thirty-one hosts by `extract_features()` in `backend/ml/pretier_features.py`, using attributes like department, role, operating system, internet-facing status, network zone, and domain suffix. If the model loads successfully and produces a prediction, those results are returned. If the model file is absent or prediction fails for any reason, the function falls back to a default response: Support mission prevalence at 0.60 confidence, and Minimal public well-being impact at 0.60 confidence. The return shape is always a dictionary with four keys: `mission_prevalence`, `mission_prevalence_confidence`, `public_wellbeing_impact`, and `public_wellbeing_confidence` — and this contract is designed never to change.

## Step 2 — Asset Context from the CMDB

With mission tags in hand, the pipeline immediately looks up the asset's data classification and internet-facing status through three helper functions in `backend/ingest_helpers.py`: `lookup_data_classification()`, `is_internet_facing()`, and `get_asset_context()`. These all delegate to the CMDB adapter in `backend/integrations/cmdb.py`, which in the current implementation reads from a mock file called `mock_cmdb.json` containing thirty-one fictional but realistic WA Government hosts. For each hostname, it returns the full set of asset metadata — network zone, operating system, role, business owner, technical owner, patch cycle dates, registered applications, dependent assets, and service account information. For unknown hostnames, it returns conservative defaults: OFFICIAL classification, not internet-facing, with empty strings for the remaining fields. This mock layer is a deliberate architectural choice — the ingest pipeline never contains CMDB lookup logic directly, making it straightforward to swap in a real configuration management database adapter when one becomes available.

## Step 3 — CWE Classification

The vulnerability itself needs a weakness classification, and that is handled by `get_cwe()` in `backend/ingest_cwe.py`. It first calls into the NVD integration in `backend/integrations/nvd.py`, which makes a request to the NVD API 2.0 endpoint, looks up the CVE identifier, and returns the CWE class from the NVD weakness enumeration data. The NVD integration has its own twenty-four-hour TTL cache to avoid redundant lookups. If the NVD lookup returns nothing — which can happen for very recent CVEs or older CVEs that lack NVD enrichment — the function falls back to a regex extraction that scans the vulnerability description for a `CWE-\d+` pattern. If both fail, it returns an empty string. The result includes the `cwe_class` key, which is then used in the EPSS substitution step, the MITRE ATT&CK mapping step, and the RAG query. A small in-process cache keyed by CVE ID is maintained in the CWE module itself, so repeated lookups for the same vulnerability within a single ingest session hit memory rather than making another NVD call or regex scan.

## Step 4 — EPSS Substitution

The Exploit Prediction Scoring System from FIRST.org gives a global, technology-agnostic probability that a CVE will be exploited in the next thirty days. But that probability is not sector-aware. A vulnerability that has a low global EPSS score might still be a critical threat to a WA Government health department because threat actors specifically target government healthcare infrastructure. The EPSS substitution module in `backend/ml/epss_substitutor.py` addresses this by calculating a sector-adjusted score.

The module has a fallback chain of four layers. The preferred model is v3, an XGBoost regressor trained on real FIRST.org EPSS data with three hundred and forty-four thousand scores, which was the best-performing model in the training pipeline. If v3 is not found on disk, it tries v2, which uses the same thirty-seven-feature layout trained on the same corpus but with an earlier training configuration. If v2 is absent, it tries v1, a simpler model with a twenty-two-feature encoding. If no ML model file exists at all, it falls back to a heuristic rule engine that applies multipliers based on CISA KEV status, CWE class, and sector-specific threat intelligence from the `CVE_ADJUSTMENTS` dictionary. The rule engine also handles the case where the scanner did not provide an EPSS score at all, generating a floor of 0.3 for KEV-listed CVEs or 0.05 as a conservative default. Substitution only activates when the raw EPSS score is below 0.10 and the sector multiplier exceeds 5.0, or when the ML model returns a meaningfully different prediction with confidence above the 0.3 threshold. The output includes a `substituted` boolean, the new score, the original score, a confidence value, and a human-readable reason string that gets stored in the database and shown to the analyst in the case view.

## Step 5 — Tier 0: The Deterministic Rule Engine

Now the pipeline hands control to `evaluate_tier_0()` in `backend/pipeline/tier_0.py`. This is the fastest stage — no model loading, no API calls, just three deterministic rules evaluated against four input values: CVSS score, CISA KEV status, EPSS score, and internet-facing flag plus data classification.

Rule one fires when the vulnerability is a CISA Known Exploited Vulnerability, the CVSS score is at least 9.0, and the asset is internet-facing. In that combination, the case is auto-resolved as Very Critical. Rule two fires when the vulnerability is KEV-listed, the EPSS score is at least 0.90, and the data classification is OFFICIAL Sensitive — the highest sensitivity tier under the WA Information Classification Policy. That also produces an auto-resolve to Very Critical. Rule three fires when the vulnerability is not KEV-listed, the CVSS is below 4.0, and the EPSS is below 0.10. That auto-resolves as Low. Everything else — any combination that does not match these three rules — is marked as ambiguous and escalated to the next tier. The threshold constants are defined at the top of the file and can be tuned without touching any logic: `KEV_CVSS_THRESHOLD`, `KEV_EPSS_THRESHOLD`, `LOW_CVSS_THRESHOLD`, and `LOW_EPSS_THRESHOLD`.

## Step 6 — Feature Vector Construction

If Tier 0 escalated the case, `build_feature_vector()` in `backend/ingest_helpers.py` assembles a forty-two-key dictionary by pulling data from every integration. Nine features come from the CVSS vector components plus the base score. EPSS is a single feature. Patch status contributes five: availability, OSV fixed versions, OSV package, OSV ecosystem, and a synthetic patch-applied flag derived from the CMDB last patch date. Asset context contributes five: internet-facing, domain-joined, data classification, mission prevalence, and public well-being impact. Network metrics contribute four: lateral reachability (how many hosts this asset can reach from its zone and role), boundary reachability, downstream assets count, and patch lag in days. Exploit intelligence contributes four: ExploitDB PoC status, Metasploit payload status, a synthetic internet-scan-detected flag, and the AlienVault OTX pulse count. CVE metadata contributes four: NVD reference count, description token length, vulnerability age in days, and vendor popularity index. Two CVSS vector sub-scores are included: exploitability and impact. Six boolean signature flags are set via regex against the description: MITRE Top 25 CWE membership, plus RCE, privilege escalation, auth bypass, denial of service, and path traversal signatures. The threat intel status sub-dict records scan and pulse status as strings. Finally, the raw description text is kept as a separate key for the SBERT embedding model.

## Step 7 — Tier 1: XGBoost ML Evaluation

With the feature vector ready, the pipeline calls `evaluate_tier_1()` in `backend/pipeline/tier_1.py`. This function attempts to load and run the trained XGBoost model from `backend/ml/xgboost_predictor.py`. The model uses eight hundred trees with a maximum depth of four, takes the thirty-seven tabular features plus a three hundred and eighty-four-dimensional SBERT embedding for a total input dimensionality that is reduced via PCA to thirty-two components, and outputs an exploitation probability between zero and one. That probability passes through Platt calibration to produce a confidence score.

The critical design element here is ensemble variance routing. The XGBoost model is an ensemble of decision trees; for each vulnerability, it produces eight hundred individual tree predictions. The standard deviation of those eight hundred predictions is calculated. If the standard deviation exceeds 0.15, it means the trees disagree substantially — the model is uncertain even though it might have produced a middling probability. In that case, the result is escalated to Tier 2. If the standard deviation is low and the probability is confidently below the threshold, the case is auto-resolved. If the model file is missing for any reason, the function falls back to a heuristic that computes `CVSS over 10 times 0.4 plus EPSS times 0.3` as a base score, then applies environmental adjustments for internet-facing status, lateral reachability, domain join status, mission prevalence, and well-being impact. The heuristic is deliberately conservative, escalating anything above 0.30 exploitation probability if confidence is low.

## Step 8 — RAG Query Against Internal Documentation

Before Tier 2 runs, and after Tier 1 has returned its results, the pipeline queries the RAG vector store using `query_rag()` in `backend/ingest_helpers.py`, which delegates to the same function in `backend/ml/vector_store.py`. The vector store is a LanceDB database — an in-process, embedded vector database that stores Arrow-format data on disk. It holds pre-computed embeddings of internal documentation: CMDB records, change management entries, GPO reports, and security baseline documents for the demo hosts. There are nine seed documents in the current store, covering assets like the MOVEit file transfer server, the Citrix ADC appliance, the PaperCut print server, and generic WA Government security baseline documents.

The query is constructed from the hostname and the CWE class, then embedded using the same `all-MiniLM-L6-v2` SentenceTransformer model that powers the XGBoost pipeline. LanceDB performs a vector similarity search returning the top three results. If the vector search fails for any reason — the store is empty, the table does not exist, or the search throws an exception — the function falls back to a full-text search index that LanceDB maintains alongside the vector index. Results are cached per hostname with a sixty-second TTL, so concurrent ingest requests for different CVEs on the same asset do not hammer the vector store. The returned `rag_context` string, capped at five thousand characters, is injected into the Tier 2 prompt to give the language model situational awareness about the asset's configuration, patch status, and mitigating controls.

## Step 9 — Tier 2: Cloud LLM Semantic Analysis

If Tier 1 escalated, `evaluate_tier_2()` in `backend/pipeline/tier_2.py` builds a force-reflection prompt split into a cacheable system message and a dynamic user message. The language model performs a three-step analysis: primary exploitability assessment, counter-argument for mitigating constraints, and final determination weighing both sides. The provider chain tries OpenAI `gpt-4o-mini` first, then Anthropic `claude-haiku-4-5` as backup, then Together AI as tertiary. Each provider retries up to three times with exponential backoff. If all fail, a `KNOWN_CONFLICTS` dictionary covers three hardcoded CVEs — CVE-2023-36884 (score adjustment negative fifteen), CVE-2023-22515 (negative thirty-seven), and CVE-2022-47966 (negative sixty-six) — and returns a neutral default for everything else.

The score adjustment returned by the LLM is clamped to the range negative seventy to positive ten before being applied to the final score. The bias toward negative adjustments is deliberate — the LLM is asked to identify mitigating constraints that would reduce a vulnerability's priority. Positive adjustments are rare and reserved for cases where the LLM identifies an amplifying factor that the upstream pipeline missed.

## Step 10 — Final Score Calculation

With results from all stages that ran, the pipeline calls `calculate_final_score()` in `backend/scoring.py`. The scoring engine combines six weighted dimensions into a single zero-to-one-hundred priority score. CVSS contributes up to forty points, calculated as the CVSS score divided by ten multiplied by forty. EPSS contributes up to twenty points, using the substituted EPSS score if one was generated. Asset criticality contributes up to twenty points, built from data classification (twelve points for OFFICIAL Sensitive, four for OFFICIAL), mission prevalence (six for Core, two for Support), and public well-being impact (two for Severe, one for Moderate). Exposure contributes up to fifteen points, with twelve points for internet-facing assets and three for internal ones. Patch status contributes up to five points — five if a patch is available and has been applied, zero otherwise. The ML exploitation probability contributes up to ten points, based on the Tier 1 prediction. The Tier 2 score adjustment, clamped to plus or minus twenty, is added after the sum. The total is clamped to the range zero to one hundred and mapped to a band: zero to twenty-five is Low, twenty-six to fifty is Medium, fifty-one to seventy-five is Critical, and seventy-six to one hundred is Very Critical.

## Step 11 — Detection Tier Label

The pipeline assigns a detection tier label based on which stages ran to completion. If Tier 0 auto-resolved the case, the label is Deterministic. If Tier 0 escalated and Tier 1 resolved it (with or without ensemble variance routing), the label is ML Tier. If Tier 0 escalated, Tier 1 escalated, and Tier 2 returned a result, the label is SLM Tier. This label is stored in the database and displayed in the queue table and the case view header.

## Step 12 — MITRE ATT&CK Mapping

The CWE class from step 3 is looked up in a static mapping in `backend/integrations/mitre_mapping.py`. The mapping covers twenty-four CWEs, each mapped to between one and three MITRE ATT&CK techniques with technique ID, name, and description. For example, CWE-89 (SQL injection) maps to T1190 (Exploit Public-Facing Application) and T1505.003 (Web Shell). CWE-78 (OS command injection) maps to T1202 (Indirect Command Execution). CWE-287 (authentication bypass) maps to T1078 (Valid Accounts). If the CWE class is not in the mapping, an empty list is returned and the mitre_techniques_json column stores an empty array. The mapping is static and process-lifetime — there is no live API call to MITRE's ATT&CK database.

## Step 13 — Advisory Reference and Summary Paragraphs

The pipeline builds an advisory reference by calling `get_advisory()` in `backend/integrations/advisories.py`, which currently returns stub data from an in-memory dictionary keyed by CVE ID. It also calls `_build_summaries()` to generate three narrative summary paragraphs explaining the case, the asset mission classification, and the pipeline routing decision. These paragraphs are stored as JSON in the database and displayed in the case view's top panel.

## Step 14 — Audit Selection and Database Insert

Before the record hits the database, the pipeline calls `should_audit()` from `backend/audit.py`. This function randomly selects approximately 7.5 percent of auto-resolved cases for independent review, using Python's random module with a fixed sample rate constant. If selected, an `audit_selected` flag is set on the database row. The audit queue is surfaced in the frontend's review screen, and analysts can record a pass or fail result against each flagged case. After the audit check, the full row — all fifty-plus columns covering every stage of pipeline output — is inserted into the `vulnerabilities` table using parameterised SQL. The `lastrowid` from the insert is used to build the response, which includes both a `QueueRow` for the table display and a `CaseViewData` object containing all the enriched data for the case detail screen.

## What's Planned for the MVP

The ingest pipeline is functionally complete — every step from pre-tier classification through audit sampling is wired and producing results. What remains for the MVP window is operational hardening.

The daily low-severity re-check already runs as a background asyncio task, querying for rows classified as Low more than seven days ago and re-running Tier 0 with current values. The planned work extends it to poll for updated EPSS scores from the FIRST.org API rather than only using the stored score. The 7.5 percent audit sampling rate, currently hardcoded in `backend/audit.py`, will become configurable via environment variable.

The most impactful planned change is inverting the pre-tier priority order: try the trained random forest model first, fall back to the `KNOWN_TAGS` dict, then to defaults. The model file exists at `backend/ml/pre_tier_model.pkl` and the code path is written, but the dict currently takes priority, so the model never runs for the thirty-one known hosts. Flipping this order makes the pre-tier classifier genuinely adaptive.

The EPSS substitution v3 model, trained on three hundred and forty-four thousand real FIRST.org scores, will be retrained on the latest EPSS data with additional CWE and agency feature encodings. The token-bucket rate limiter in `backend/middleware/rate_limit.py` will also gain environment-variable configuration for ingest rates, replacing the current hardcoded limits.
