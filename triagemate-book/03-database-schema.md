# Chapter 3: Database Schema

Welcome back. In Chapter 2 we traced the ingestion pipeline from raw scanner upload through the three-tier enrichment engine to the final priority score. Now we open the hood on where all that data actually lives. TriageMate's database is a deliberately simple, pragmatic design. Three tables. Two SQL dialects. Zero foreign key constraints. Let's walk through every column and understand why it's there.

## The Big Picture

TriageMate uses two database backends transparently. In development and single-user deployments, it's SQLite — a single file called `triagemate.db`. In production with multiple analysts hitting it simultaneously, it's PostgreSQL. The switch is controlled by a single environment variable, `DATABASE_URL`. Set it to a `postgresql://` connection string, and the whole stack flips to PostgreSQL without changing a single line of application code. This dual-dialect pattern is baked into the schema layer itself: every DDL statement exists in two flavours — `_init_db_sqlite()` and `_init_db_pg()` — and both must be updated for any schema change.

The database has three user-facing tables and one internal housekeeping table. The workhorse is `vulnerabilities`, holding every active vulnerability record. When an analyst clears a finding, it moves to `resolved_vulnerabilities` — a historical archive that mirrors the schema almost exactly. Every manual review action — override, reclassify, add a note — is logged to `reviews`, an append-only audit trail. And `alembic_version` is Alembic's single-column migration tracker, currently sitting at migration 005.

## The `vulnerabilities` Table — 72 Columns

This is where the action lives. Every vulnerability ingested through the pipeline ends up here. Seventy-two columns sounds like a lot, but they break down into logical groups that map directly to the pipeline stages we covered in Chapter 2.

### Core Identity

Every vulnerability needs to be uniquely addressable. The `id` column is an auto-incrementing integer primary key — `SERIAL` in PostgreSQL, `INTEGER PRIMARY KEY AUTOINCREMENT` in SQLite. This is the internal row identifier used everywhere in the application. The `vulnerability_id` column holds the CVE identifier, like `CVE-2024-12345`. And `hostname` is the fully qualified domain name of the affected asset. These three columns together are what you'd show in a scan report summary: "CVE-2024-12345 on webserver01.acme.org."

### Tier 0 — Raw Inputs

Tier 0 is the raw, untouched data from the scanner and external feeds. `cvss_score` is a real number — the CVSS base score from NVD. `cvss_vector` is the full vector string like `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`. `cisa_kev` is a boolean: true if this CVE is listed in CISA's Known Exploited Vulnerabilities catalogue. And `epss_score` is the Exploit Prediction Scoring System probability — a number between 0 and 1 representing the likelihood of exploitation in the wild.

These are the foundation everything else builds on. CVSS tells you severity in a vacuum. EPSS tells you real-world exploitation likelihood. CISA KEV tells you the US government is paying attention. Each feeds into the scoring model differently.

### Pre-Tier Predictions

Before any tier processing, the system makes two high-level predictions. `mission_prevalence` is a text field — something like "Widespread" or "Targeted" — indicating how broadly this vulnerability affects the organisation. `mission_prevalence_conf` is the confidence in that prediction, 0.0 to 1.0. Similarly, `public_wellbeing_impact` is a text assessment of potential real-world harm, and `public_wellbeing_conf` is its confidence score. These predictions are generated by the enrichment engine's upstream analysis and fed into the tier pipeline as context.

### Tier 0 Outputs

After initial triage, Tier 0 decides where this vulnerability should go. `tier_0_routing` is a text label — "Tier 1" if it needs deeper analysis, "Auto-Resolve" if it can be closed immediately based on rules, or "Escalate" if it needs human attention. `tier_0_resolution` captures the resolution action if Tier 0 closed the case. These two columns represent the first fork in the decision tree.

### Tier 1 Outputs

Tier 1 is the ML-based enrichment layer. `tier_1_confidence` is the model's confidence in its assessment, 0.0 to 1.0. `tier_1_exploitation_prob` is a separate probability estimate focused specifically on exploitation likelihood — derived from ML analysis of the CVE description, affected software, and exploit databases. `tier_1_routing` decides the next step: route to Tier 2 for LLM-based analysis, or close with a recommendation.

### Tier 2 Outputs

Tier 2 is the SLM (Small Language Model) layer, and it's where things get nuanced. `tier_2_text_conflict` is a boolean flag — true if the SLM detected a contradiction in the vulnerability description or advisory text. `tier_2_conflict_note` is the free-text explanation of that conflict. `tier_2_rag_result` holds the retrieval-augmented generation result — relevant chunks from the knowledge base. `tier_2_confidence` is the SLM's confidence in its overall assessment. And `tier_2_resolution_summary` is a human-readable summary of what Tier 2 recommends doing.

### Final Scoring

The output everyone cares about. `priority_score` is an integer from 0 to 100 — the final priority score computed by the scoring engine. `risk_band` is a text label: `Low`, `Medium`, `Critical`, or `Very Critical`. These four bands map to score ranges: 0-25 is Low, 26-50 is Medium, 51-75 is Critical, 76-100 is Very Critical. Together they give analysts an at-a-glance triage signal.

### Scoring Dimensions

The priority score isn't a black box. Six dimension columns break down exactly how the score was built. `cvss_contribution` maxes out at 40 points — the base severity weight. `epss_contribution` maxes at 20 points — the real-world exploitation likelihood. `asset_criticality_contribution` also maxes at 20 — how important the affected asset is to the mission. `exposure_contribution` maxes at 15 — whether the vulnerability is internet-facing or internal only. `patch_remediation_contribution` maxes at 5 — how quickly a fix is available. And `ml_exploitation_contribution` maxes at 10, defaulting to 0 — the ML model's independent exploitation probability assessment, added in migration 005 to give the ML pipeline a direct voice in scoring.

### EPSS Substitution Tracking

EPSS isn't always available. For new CVEs or obscure software, there may be no EPSS score yet. When that happens, the system substitutes a computed estimate. `epss_substituted` is a boolean flag indicating a substitution occurred. `epss_substituted_value` holds the substituted score. `epss_substitution_confidence` is confidence in the substitution. And `epss_substitution_reason` explains why — "No EPSS data for CVE; derived from similarity to CVEs in same CWE" for example.

### Asset Context — 15 Columns

This block brings in asset registry context. Fifteen columns capturing everything about the affected host. `data_classification` — is this system handling classified, sensitive, or public data? `network_zone` — DMZ, internal, restricted? `interface_type` — is it a web interface, API, command line? `patch_cycle` — monthly, quarterly, exception-only? `last_patch_date` and `last_scan_date` track operational cadence. `operating_system` and `role` describe the host itself. `business_owner` and `technical_owner` are the people responsible. `registered_applications` lists what applications run on this host. `dependent_assets` captures downstream dependencies. And `service_account` is the service account the application runs under.

This context feeds directly into the asset criticality dimension of the priority score. A domain controller handling classified data in the DMZ with no patch in six months scores much higher on criticality than a dev sandbox on an isolated network.

### Detection Pipeline

How did this vulnerability get detected and enriched? `detection_tier` is a text label: `Deterministic`, `ML Tier`, or `SLM Tier`. `detection_reason` explains the routing decision — for example, "Deterministic match on CISA KEV with CVSS >= 9.0."

### JSON Payload Columns

Nine columns store structured data as JSON text strings. SQLite has no native JSON column type, and using PostgreSQL's JSONB would break the dual-dialect pattern. So everything is stored as TEXT and parsed at the application layer. `scanner_output_raw` holds the full original scanner finding. `weakness_template_raw` holds the weakness analysis template. `advisory_ref_id` and `advisory_quote` capture the relevant advisory reference and quote. `investigation_notes` stores analyst investigation notes. `mitre_techniques_json` is a list of MITRE ATT&CK technique objects, each with `id`, `name`, and `desc` fields. `scoring_weights_json` is a list of scoring dimension breakdowns, each with `name`, `awarded`, `max`, `justification`, and `is_substituted`. `asset_registry_json` is a list of key-value pairs from the asset registry. And `summary_paragraphs_json` is a list of summary text strings for the analyst dashboard.

### Timestamps and Operational Fields

`created_at` and `updated_at` are timestamps defaulting to `CURRENT_TIMESTAMP`. `last_recheck_date` tracks when this vulnerability was last rechecked against current data. Three audit columns — `audit_selected` (boolean), `audit_result` (text), and `audit_date` (text) — support the background audit feature that randomly samples vulnerabilities for quality assurance.

### Analytics Columns

Added in migration 002, `analytics_view_count` is an integer counter incrementing each time a vulnerability is viewed, and `analytics_last_viewed` is a timestamp of the most recent view. These support the "most viewed" and "recently viewed" filters on the analyst dashboard.

### Review Queue Columns

Added in migration 004, seven columns support the manual review workflow. `flagged_for_review` is a boolean — analyst tools or automatic rules set this to true when a vulnerability needs human review. `review_status` tracks the review state — "Pending", "In Progress", or "Completed". `review_decision` captures what the reviewer decided — "Confirmed", "Reclassified", or "False Positive". `reviewed_by` and `reviewed_at` record who did it and when. And `override_score` and `override_band` let the reviewer manually override the computed priority score and risk band. This is the escape hatch: the scoring engine computes, but the analyst decides.

## The `resolved_vulnerabilities` Table — 74 Columns

This table is the archive. When a vulnerability is cleared via `POST /api/ingest/clear`, the entire row is copied from `vulnerabilities` to `resolved_vulnerabilities` and deleted from the active table. The schema mirrors `vulnerabilities` with three deliberate differences.

First, an `original_id` column holds the `id` value from the original `vulnerabilities` row — a breadcrumb back to the source record. Second, `created_at` and `updated_at` are stored as plain `TEXT` rather than auto-generating timestamps. They're copied as-is from the original row, preserving the exact values at the time of resolution. Third, two extra columns are added: `resolved_at` defaults to `CURRENT_TIMESTAMP` and records when the clear happened, and `resolution_reason` defaults to `'demo_clear'` and captures why — in production this would be something like "Patch confirmed" or "Risk accepted by ISSO."

The result is a fully self-contained historical record. You can archive a vulnerability today, and six months later every detail of what was known at the time of resolution is still available, including the original scoring dimensions, asset context, audit data, and review decisions. This is critical for compliance reporting and post-mortem analysis.

## The `reviews` Table — 9 Columns

This is the audit log. Every time an analyst takes a manual action on a vulnerability, a row is appended to `reviews`. It's a narrow table with a single purpose: immutable traceability.

`id` is the auto-incrementing primary key. `vulnerability_id` is the CVE identifier — denormalised here so you can query all reviews for a CVE without joining. `case_id` is the integer primary key from either `vulnerabilities` or `resolved_vulnerabilities`, identifying the specific case. `analyst_decision` is a required text field capturing the action — "Override Score", "Override Band", "Flag for Review", "Confirm", "Reclassify", or "False Positive". `override_score` and `override_band` capture the analyst's new values if they changed the scoring. `notes` is free text. `analyst_name` identifies who acted. And `created_at` timestamps the action.

This table supports the full audit trail requirement. Any compliance question like "Who overrode the priority score on CVE-2024-12345 and why?" is a simple query against `reviews` filtered by `vulnerability_id` and sorted by `created_at`.

## The Migration Engine

Schema changes go through Alembic. The `alembic_version` table has a single column `version_num` holding the current revision string — currently `005`. When `init_db()` is called at application startup, it first tries `run_migrations()`, which invokes Alembic's `command.upgrade(cfg, "head")`. If Alembic is not installed or the migration fails, it falls back to inline DDL via `CREATE TABLE IF NOT EXISTS`.

There are five migrations to date. Migration 001, dated 2026-06-30, created the initial `vulnerabilities` table with the first 56 columns. Migration 002, same day, added the two analytics columns. Migration 003, on 2026-07-02, created the `resolved_vulnerabilities` table. Migration 004, also 2026-07-02, added the seven review queue columns to both tables and created the `reviews` table. Migration 005, same day, added `ml_exploitation_contribution` to both tables.

### The Dual-Dialect Pattern

Every schema addition requires updating two methods: `_init_db_sqlite()` and `_init_db_pg()`. SQLite uses `INTEGER PRIMARY KEY AUTOINCREMENT`, `REAL`, `BOOLEAN`, `TIMESTAMP`, and `?` placeholders. PostgreSQL uses `SERIAL PRIMARY KEY`, `REAL`, `BOOLEAN`, `TIMESTAMP`, and `%s` placeholders. The `_PGCursor` class wraps psycopg2 and converts `?` to `%s` automatically, so application code can use `?` everywhere and work against both backends.

The `_PGCompatRow` class provides dict-style access (`row["column_name"]`) and tuple-style access (`row[0]`) for PostgreSQL results, mirroring `sqlite3.Row` exactly. The `_PGConnection` wrapper adds a convenience `execute()` method to psycopg2 connections, so the same `conn.execute(sql, params)` pattern works for both SQLite and PostgreSQL. This compatibility layer means the entire application codebase — all routes, services, and background jobs — never needs to know which database is running underneath.

### Relationships — By Convention, Not Constraint

There are no database-level foreign key declarations in TriageMate. Even though `PRAGMA foreign_keys=ON` is set for SQLite, no `REFERENCES` clauses appear anywhere. The `reviews.case_id` references `vulnerabilities.id` or `resolved_vulnerabilities.id` by application convention. The `resolved_vulnerabilities.original_id` references `vulnerabilities.id` by convention. The `vulnerabilities.hostname` references the asset registry by convention.

This is deliberate. The application layer enforces referential integrity, and avoiding database-level constraints keeps the schema simple, avoids migration ordering headaches, and lets us delete and archive rows without constraint cascading. There are no triggers and no secondary indices — the only auto-generated index is on `alembic_version`. The application is small enough that full table scans on 72-column rows are acceptable at current scale.

## What's Planned

The inline DDL in `database.py` is currently a subset of the authoritative schema. It includes `ml_exploitation_contribution` from migration 005 but is missing the analytics columns from migration 002 and the review queue columns from migration 004. This gap between the inline DDL and the Alembic migrations means that anyone running with Alembic unavailable gets the old 62-column schema — functional but incomplete. Updating the inline DDL to match the full 72-column schema after all five migrations is on the near-term roadmap.

Future schema changes will follow the dual-database DDL pattern established here. Every new column gets added in an Alembic migration, mirrored in both `_init_db_sqlite()` and `_init_db_pg()`, and wrapped in the compatibility layer. The pattern is well-established: add the column to both DDL methods, add the migration script, test against SQLite, test against PostgreSQL, ship.

One area under active discussion is indexing. As the vulnerability count grows — especially `resolved_vulnerabilities` — the lack of indices on commonly queried columns like `vulnerability_id`, `hostname`, and `risk_band` will become a performance bottleneck. Intent-based indexes (defined declaratively, generated per dialect) are likely the next infrastructure investment.

Another planned improvement is formalising the relationship between `reviews.case_id` and the two vulnerability tables. Currently the `case_id` could reference either `vulnerabilities.id` or `resolved_vulnerabilities.id` with no way to distinguish them in a query without additional logic. Adding a `case_type` column to `reviews` — `'active'` or `'resolved'` — would make join logic explicit and queryable.

## What It All Means

The TriageMate schema is a document of the pipeline. Read the columns from top to bottom and you trace the entire ingestion journey: raw scanner data, external feed enrichment, ML analysis, SLM analysis, scoring computation, asset context overlay, audit tracking, review workflow. Every stage of the pipeline adds its output to the row. When you look at a single row in `vulnerabilities`, you're looking at the complete history of how that vulnerability was processed — every enrichment step, every confidence score, every routing decision, every dimension contribution.

Three tables. Two dialects. Zero constraints. That's the schema. In the next chapter, we'll look at how the application layer interacts with this schema — the API patterns, the query patterns, and the design decisions that keep the data layer simple even as the pipeline grows.
