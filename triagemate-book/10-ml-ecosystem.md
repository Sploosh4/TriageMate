# Chapter 10: The ML Ecosystem

**Target:** 1500–3000 words · Self-contained · Podcast-script style · ~70/30 implemented-to-planned

---

You have made it to the machine learning layer. This is where TriageMate stops being a fancy rule book and starts being an intelligent system. There are five ML components in the codebase right now. Some are active in production, some are trained but waiting for activation, and one is a pretrained model we download and never train ourselves. By the end of this chapter you will know exactly what each one does, how they connect, and what is coming next.

Let me start with the workhorse — the Tier 1 XGBoost exploitation probability model. This is the model that answers the single most important question in the pipeline: given everything we know about a vulnerability and the asset it lives on, how likely is it to be exploited in the next thirty days?

The model is an XGBoost classifier with eight hundred trees, each with a maximum depth of four. Eight hundred is a lot of trees for a tabular dataset, but XGBoost handles it gracefully with column subsampling and early stopping built into the training loop. The training data consists of 186,102 CVEs drawn from the NVD corpus, spanning 2019 through 2024. Each CVE starts as raw JSON from NVD's API 2.0 and goes through an elaborate pipeline of enrichment before it ever sees a gradient. First we merge in the EPSS score from FIRST.org. Then we merge in CISA's KEV catalogue. Then we run the CVE description through a Sentence-BERT model — specifically all-MiniLM-L6-v2 — which produces a 384-dimensional embedding of the English description text.

Here is where it gets interesting architecturally. The feature vector for each CVE has sixty-eight dimensions. Thirty-five of those are tabular features — CVSS metrics encoded numerically, EPSS probability, patch availability, asset context flags like internet-facing and domain-joined, exploit intelligence signals like whether there is a Metasploit module or an ExploitDB proof-of-concept, CVE metadata like reference count and vulnerability age, signature patterns detected in the description text, and a MITRE Top 25 CWE indicator. The remaining thirty-three are the 384-dimension SBERT embedding — wait, let me correct myself. The tabular part is 35 dimensions. The text part is 384 dimensions from SBERT. That makes 419 total. But the user's instructions say 68 features (35 tabular + 384-dim SBERT → PCA removed). Actually looking at the code more carefully, what happened is that an earlier version used PCA to reduce the SBERT output from 384 to 33 dimensions, making the total 35 + 33 = 68. Then in v2.5 of the training pipeline, PCA was removed entirely because it introduced data leakage — the PCA transform was fitted on the entire dataset including the test split. So the current pipeline stacks the full 384-dimensional SBERT vectors directly onto the 35 tabular features, giving 419 total dimensions. XGBoost handles this fine because its column subsampling and max depth regularization prevent overfitting on the high-dimensional text features.

The training script, train_xgboost.py, is 1,195 lines in two phases. Phase 1 fetches CVEs from NVD in quarterly chunks, merges EPSS and KEV, builds tabular features, encodes descriptions with SBERT, and saves training_data.npz. Phase 2 loads that data, splits chronologically — train before June 2023, validation June to December 2023, test after — trains XGBoost, applies Platt scaling via LogisticRegression on validation probabilities, tunes the decision threshold for F1, and exports xgboost_model.pkl and xgboost_calibrator.pkl.

The calibration step matters because XGBoost probabilities are poorly calibrated for imbalanced datasets. Platt scaling maps raw outputs to better-calibrated probabilities, and threshold tuning picks the F1-maximising cutoff. The calibration audit in analysis/calibration_audit.py recomputes Expected Calibration Error against the full enriched CVE dataset, producing per-bin diagnostics showing where the model is overconfident or underconfident.

Now, the second model. The Pre-Tier Random Forest classifier lives in the pipeline before Tier 0 even runs. Its job is to take a hostname and classify it along two dimensions: mission prevalence — either Core, Support, or Peripheral — and public wellbeing impact — either Severe, Moderate, or Minimal. These two tags feed directly into the scoring engine and influence every downstream tier.

The model is a MultiOutputClassifier wrapping a RandomForestClassifier. The Random Forest has 200 trees internally, though the training script refers to 150 trees in its documentation — the actual code uses 200 estimators with max_depth=None, min_samples_leaf=2, and balanced class weights. The training data consists of 242 original WA Government hostname records plus 300 synthetic supplemental records generated by a script called generate_supplemental_hostnames.py. Each record has a hostname, a mission label, and a wellbeing label. The features are extracted from the hostname string itself. The feature extraction module, pretier_features.py, parses the hostname into 55 dimensions. It extracts the environment code from the first token (PRD, STG, DEV, TST), one-hot encodes the agency from the subdomain, checks for role keyword patterns like web, app, db, dc, file, and so on, derives a heuristic data classification code from keyword matching, guesses whether the asset is internet-facing based on presence of web or portal indicators, detects network zone from subdomain labels, checks for domain controller indicators, detects extended lifecycle flags like EOL, SUN, MIG, and ACT, checks for OS platform indicators embedded in the hostname, detects role suffix patterns like AP01 or DB01, and checks for known WA Government system names.

The model file is pre_tier_model.pkl, and it is trained offline by train_pre_tier.py, which is 354 lines. The training pipeline includes stratified five-fold cross-validation and prints per-fold accuracy for both mission and wellbeing classification. On the full training set, the model achieves high accuracy — though this is on synthetic and hand-labelled data, so those numbers should be taken with a grain of salt until real operational feedback comes in.

Here is the key caveat: this model is NOT active in the pipeline. The Pre-Tier stage in pre_tier.py still uses a dictionary called KNOWN_TAGS as its primary data source. KNOWN_TAGS has hardcoded entries for 31 known demo hosts — the original 7 plus 24 more added during development. Each entry maps a hostname directly to its mission and wellbeing labels with confidence scores. The model file is loaded if it exists, and it is used as a fallback for hostnames that are not in the dictionary. But the dictionary covers the demo corpus completely, so the model never actually fires during normal operation. Activating the model — making it the primary classifier and retiring the dictionary — is a planned task for Sprint NEXT.

The third family of models is the EPSS substitution models. There are three versions, and they form an inference chain. EPSS — the Exploit Prediction Scoring System from FIRST.org — is a global exploitation probability. It is not sector-aware. A CVE that disproportionately targets healthcare organisations gets the same EPSS score as any other CVE. The EPSS substitution models adjust raw EPSS scores based on sector-specific context: which WA Government agency the asset belongs to, which CWE class the vulnerability falls into, whether it is in CISA KEV, what the exploit maturity level is, whether a public proof-of-concept exists, and the vendor patch status.

The current best model is v3. It is an XGBoost regressor with 300 trees and a maximum depth of eight. It was trained on 344,852 real EPSS scores from FIRST.org, each combined with synthetic sector context. The key insight of v3 is that it grounds the training in real EPSS data rather than in the rule engine's own outputs. The v2 model, which preceded it, was trained on purely synthetic data generated by the same rule engine it was supposed to replace — a circular dependency that limited its value. The v3 training script, train_epss_v3.py, is 393 lines. It loads the real EPSS cache, generates 2,000 training samples by drawing random real CVE baselines and adding synthetic sector context, trains the XGBoost regressor, and exports the model as epss_model_v3.pkl. The feature vector has 37 dimensions: raw EPSS score, CVSS score, exploit maturity level, CISA KEV flag, public PoC flag, vendor patch status, an 11-element one-hot encoding for agency, and a 20-element one-hot encoding for CWE class.

The v2 model uses the same 37-feature layout — it is a drop-in replacement at inference time. Its training script, train_epss_v2.py, is 543 lines and generates 1,000 synthetic samples. The v1 model uses a smaller 22-feature layout with fewer agencies and CWEs. Its training script, train_epss_substitutor.py, is 337 lines.

The substitution logic lives in epss_substitutor.py, which is 673 lines. On import, it tries to load v3 from disk. If v3 is not available, it falls back to v2. If v2 is not available, it falls back to v1. If none of the models are available, it falls back to a heuristic rule engine that applies hardcoded CVE-specific adjustments, CWE multipliers, and a CISA KEV multiplier. Each model's prediction comes with a confidence score. If the confidence is below a threshold of 0.3, the result is discarded and falls through to the rule engine. This chain ensures that the substitution system degrades gracefully from the most sophisticated model to the simplest heuristic.

The fourth component is the SBERT text embedder. This is not a trained model in the traditional sense — it is a pretrained SentenceTransformer model downloaded from Hugging Face, specifically all-MiniLM-L6-v2. It produces 384-dimensional embeddings of CVE descriptions. It is used by both the XGBoost model and the LanceDB vector store. The embedder follows a lazy-loaded singleton pattern with a threading lock, which is the same pattern used by every ML component in the system. On first call to encode_description or encode_batch, it checks whether the embedder has been loaded. If not, it acquires the lock, loads the model from disk or downloads it if necessary, and caches it in a module-level global variable. If the download fails — which can happen on an air-gapped network — it falls back to returning zero vectors. The SBERT model itself is approximately 90 megabytes and runs on CPU exclusively.

The fifth component is the LanceDB vector store. This is TriageMate's internal documentation retrieval system, used for RAG — retrieval-augmented generation — context injection in the Tier 2 LLM analysis. LanceDB is an in-process vector database built on Apache Arrow. It requires no server, no network port, and no external dependency beyond the lancedb Python package. The vector store lives on disk at backend/data/lancedb and stores 384-dimensional embeddings with associated metadata.

The store has been seeded with nine documents — seven host-specific CMDB records for the original demo hosts (MOVEit, Citrix ADC, PaperCut, ScreenConnect, file store, Confluence wiki, ManageEngine ITSM) plus two generic security baselines for WA Government Windows Server policy and service account management. Each document describes software version, role, interface, patch status, data classification, network zone, and dependent assets. The query_rag function constructs a semantic search query from hostname and CWE class, encodes it with SBERT, and returns the top three most similar documents. Results are cached per hostname for 60 seconds.

Now let me talk about the training data pipeline — the scripts that build the data that feeds these models. fetch_nvd_corpus.py is the bulk NVD corpus builder. It queries NVD API 2.0 in three-month chunks from 2019 through 2025, paginating through results, handling rate limits, and checkpointing progress so the fetch can be interrupted and resumed. It has a sophisticated error handling layer with five retry attempts and exponential backoff. The output is nvd_corpus.json, containing 186,102 CVE records consuming 145 megabytes of disk space. Each record includes the CVE ID, description, CVSS v3.1 score and vector, published date, CWE class, reference count, exploitability subscore, impact subscore, and reference list.

refresh_caches.py handles the live data feeds. It fetches the CISA KEV catalogue, which currently contains 1,631 entries, and the FIRST.org EPSS scores, which total 344,852 records. These are cached locally to reduce API load and ensure the pipeline can operate even when the upstream APIs are unreachable. The KEV cache is updated by pulling the official CISA JSON feed. The EPSS cache is updated by pulling the FIRST.org CSV export with pagination.

build_training_corpus.py is the unified training dataset builder. It loads nvd_corpus.json, kev_cache.json, epss_cache.json, and the ExploitDB mappings, then builds a 35-dimensional tabular feature matrix from each CVE record, concatenates it with 384-dimensional SBERT embeddings, and exports the result as training_data_v2.npz. The feature engineering logic mirrors the inference-time logic in xgboost_predictor.py exactly, including the CVSS vector parsing, the signature pattern detection regexes, and the asset context sampling. The output is used for retraining the XGBoost model.

build_vendor_index.py parses vendor names from the NVD corpus and exports a JSON mapping of vendor to popularity score for the vendor_popularity_index feature. build_cwe_hierarchy.py parses the MITRE CWE dataset into a parent-child tree for future feature engineering.

The ExploitDB integration loads a CSV export of 47,089 exploit records, of which 25,037 have CVE mappings. It builds an in-memory dict mapping CVE IDs to exploit lists, feeding the exploitdb_has_poc and metasploit_has_payload features.

Now let me talk about the feature vector contract. build_feature_vector in ingest_helpers.py returns exactly 42 top-level keys spanning CVSS metrics, EPSS score, patch status, OSV fields, asset context (internet_facing, domain_joined, data_classification, mission_prevalence, wellbeing), network metrics (lateral, boundary, downstream reachability), exploit intelligence (exploitdb, metasploit, internet scan, threat intel pulses), CVE metadata (reference count, description tokens, age, vendor popularity), CVSS subscores, signature classification booleans (RCE, privesc, bypass, DoS, traversal), a nested threat_intel_status dict, and the raw description text.

The contract rule is simple and immutable: once a feature key is released, it is never renamed or removed. New keys can only be appended. This is enforced by the feature-vector-spec skill in the opencode configuration. The reason is the XGBoost model expects a fixed-dimension input. If you rename a feature, the model breaks because the new vector has a different column arrangement than what the model was trained on. If you remove a feature, the model breaks because it expects a higher dimensionality than what the pipeline provides. The only safe operation is appending a new feature to the end of the vector, then retraining the model so the new version expects the new dimension.

The lazy-loading singleton pattern is used by every ML component. The XGBoost model, the Platt calibrator, the SBERT embedder, the Pre-Tier Random Forest, the EPSS substitution model — all follow the same structure. A module-level variable starts as None. A threading lock protects the loading. On first call to the predict or encode function, the component checks the variable, acquires the lock if needed, loads the pickle file from disk, and caches it. If the file does not exist or fails to load, the component falls back gracefully — the XGBoost predictor falls back to a heuristic evaluation function in tier_1.py, the Pre-Tier model falls back to the KNOWN_TAGS dictionary, the EPSS substitutor falls back to the rule engine, and the SBERT embedder returns zero vectors. This means the entire ML layer can be absent — the file never trained, the model never downloaded — and the pipeline still runs. It produces lower-quality results, but it runs.

Now let me cover what is planned. Sprint NEXT has five ML-focused deliverables.

The single highest-impact improvement is retraining the XGBoost model on the training_data_v2.npz dataset. The current model was trained on a dataset synthesised from NVD metadata with stochastic sampling for asset-context features. The v2 dataset is built by build_training_corpus.py, which uses real data distributions wherever possible — real EPSS scores from the local cache, real KEV entries, real ExploitDB mappings, real vendor popularity from the built index. The v2 dataset also includes the osv_lead_days feature, which captures how early Open Source Vulnerability notifications arrive relative to NVD publication. The retrained model will have access to 186,000 records with more realistic feature distributions, which should improve both ROC-AUC and calibration.

The second deliverable is activating the Pre-Tier Random Forest model. This means switching the primary classification path in pre_tier.py from the KNOWN_TAGS dictionary to the ML model, with the dictionary retained only as a fallback for known-good hostnames. This will make the Pre-Tier stage generalise to any hostname, not just the 31 entries in the dictionary. The model has been trained and validated; it just needs the pipeline flag to be flipped.

The third deliverable is retraining the EPSS substitution v3 model on a larger and more representative set of training data. The current v3 was trained on 2,000 samples drawn from the 344,852 real EPSS scores. A retrained version with more samples, better coverage of the CWE and agency space, and fine-tuned hyperparameters should produce lower RMSE and higher R-squared.

The fourth deliverable is a model rollback mechanism. The current system loads the latest model file by convention — xgboost_model.pkl always points to the current model. If a retrained model performs worse than its predecessor, reverting requires manual file management. The plan is to introduce dated filenames — xgboost_model_2026-07-03.pkl — and a command-line flag, --rollback YYYY-MM-DD, that instructs the loader to use a specific dated version. This allows safe retraining with a known fallback path.

The fifth deliverable is a model comparison endpoint — GET /api/model/info — that exposes training date, ROC-AUC, recall, precision, and calibration metrics for each loaded model. This turns model version management from a filesystem operation into an API operation. An operator can check which model is active, when it was trained, and how it is performing, all from the dashboard.

Beyond Sprint NEXT, the roadmap includes quarterly retraining cycles tied to the review queue feedback loop and continuous calibration monitoring through the drift dashboard. But that is further out. For now, the focus is on the retrained XGBoost, activating the Pre-Tier model, hardening EPSS substitution, and giving operators model version management tools.

That is the ML ecosystem. Five components sharing the same lazy-loading pattern, the same graceful degradation philosophy, and the same contract discipline around the feature vector. The models are not magic — they are gradient-boosted trees and off-the-shelf transformers, wired together with offline training pipelines and inference paths that degrade gracefully when the models are unavailable. That is what makes TriageMate's ML layer production-ready without being brittle.
