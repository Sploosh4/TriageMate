## Item 1: NVD Reference Count ≥21 Tier 0 Rule

**Effort:** 30 min | **Assignee:** strike | **Priority:** High

### What
Add a deterministic rule to `tier_0.py:evaluate_tier_0()`: CVEs with 21+ NVD references auto-resolve as `very_critical`. This is a free signal — NVD reference count is already collected and cached during ingest (via `get_cwe()` → `get_nvd_data()`).

### Why
Research shows CVEs with 21+ NVD references have 9.5× baseline KEV rate. A deterministic rule catches these high-risk CVEs at day 0, no ML needed.

### Implementation

1. **`backend/pipeline/tier_0.py`:**
   - Add `nvd_reference_count: int` parameter to `evaluate_tier_0()`
   - Add `NVD_REF_THRESHOLD = 21` constant
   - Add rule: if `nvd_reference_count >= NVD_REF_THRESHOLD` → auto-resolve `very_critical`
   - Place this as the first rule (extremely high signal, deserves highest priority)

2. **`backend/routers/ingest.py`:**
   - Call `get_nvd_data(payload.vulnerability_id)` before `evaluate_tier_0()` (line ~158)
   - Extract `nvd_reference_count` from the result
   - Pass it to `evaluate_tier_0(nvd_reference_count=...)`
   - Note: `get_nvd_data()` has 24h TTL cache. Since `get_cwe()` at step 3 already calls it, this second call is effectively free (cache hit).

3. **Tests:** Add a test file `backend/tests/test_tier0.py`:
   - Test rule fires for count >= 21
   - Test rule doesn't fire for count < 21
   - Test rule plays nicely with existing KEV/CVSS/EPSS rules

### Acceptance Criteria
- Ingest POST with CVE that has >= 21 NVD references → Tier 0 auto-resolves as `very_critical`
- Existing demo CVEs score within ±3 of 98/91/73/66/58/44/26 (source: `routers/models.py:89`, tested in `test_model_versions.py:134`)
- All 275+ existing tests still pass

## Item 2: CWE-Stratified EPSS Thresholds — Extend to Tier 0

**Effort:** 45 min | **Assignee:** strike | **Priority:** High

### What
✅ **Part A (Fix dead code) is already done** — verified by `backend/reports/intel/2026-07-10-sprint18-verification.md`. Both `"cwe_class"` and `"cisa_kev"` keys are already present in `build_feature_vector()`'s returned dict (lines 498-499 of `ingest_helpers.py`). The `_tier_zero_check()` in `xgboost_predictor.py` is now working code, not dead code.

The remaining work is **Part B**: extend CWE-stratified EPSS thresholds to Tier 0's `evaluate_tier_0()` so that the monolithic `LOW_EPSS_THRESHOLD = 0.10` becomes CWE-aware.

### Why
- The monolithic `LOW_EPSS_THRESHOLD = 0.10` applies the same bar to all CWEs
- Path Traversal (CWE-22) optimal threshold: 0.085 — CVEs at EPSS 0.09 would be mis-auto-resolved as low
- OS Command Injection (CWE-78) optimal: 0.515 — CVEs at EPSS 0.10-0.515 would be needlessly escalated
- CWE context is already computed before Tier 0 runs (step 3 in ingest.py)

### Implementation

1. **`backend/pipeline/tier_0.py`:**
   - Add `cwe_class: str = ""` parameter to `evaluate_tier_0()`
   - Import `CWE_EPSS_THRESHOLDS` from `ml.xgboost_predictor`
   - Replace monolithic `LOW_EPSS_THRESHOLD = 0.10` with CWE-aware version:
     ```python
     low_epss_threshold = CWE_EPSS_THRESHOLDS.get(cwe_class, LOW_EPSS_THRESHOLD)
     ```
   - Use the stratified threshold in the low-severity auto-resolve rule

2. **`backend/routers/ingest.py`:**
   - Pass `cwe_class=cwe_class` (already available at step 3) to `evaluate_tier_0()`

3. **Tests** (`backend/tests/`):
   - Add tests in `test_tier0.py` (or extend existing) for CWE-aware threshold behavior

### Acceptance Criteria
- Tier 0 uses CWE-specific low threshold instead of monolithic 0.10
- Existing demo CVEs score within ±3
- All 275+ existing tests pass
- Feature parity unchanged

## Item 3: Pre-Tier RF Drift Monitoring

**Effort:** 5–6 hrs | **Assignee:** strike | **Priority:** High

> ⚠️ **Effort revised upwards from roadmap's 2-4 hrs.** Critical review identified: 1hr DB migration + 0.5hr pipeline + 0.5hr ingest + 2hr reference dist script + 1hr API + 0.5hr tests = 5-6 hrs.

### What
Add PSI-based drift monitoring for the Pre-Tier Random Forest model (60-dim feature vector). This requires:
1. New DB column to store Pre-Tier feature vectors
2. Pipeline changes to capture/store them during ingest
3. Reference distribution generation
4. New `GET /api/drift/pre-tier` API endpoint
5. Tests

### Why
The XGBoost model already has PSI drift monitoring (`GET /api/drift/ml`). The Pre-Tier model and EPSS models are equally important — if their input distributions drift, prediction quality degrades silently.

### Implementation

**1. Database schema** (`backend/database.py`):
- Add `pre_tier_features TEXT` column to `vulnerabilities` table in both `_init_db_sqlite()` and `_init_db_pg()`
- Add `pre_tier_features TEXT` column to `resolved_vulnerabilities` table in both methods
- **⚠️ CRITICAL: Do NOT rely on `CREATE TABLE IF NOT EXISTS` to add columns to existing tables.** It silently does nothing on existing tables, and subsequent INSERTs will fail with "no such column."
- **Fix:** Add `ALTER TABLE` statements in `init_db()` AFTER the `CREATE TABLE IF NOT EXISTS` blocks. Use `ALTER TABLE ... ADD COLUMN pre_tier_features TEXT;` with an `IF NOT EXISTS`-style guard (SQLite ignores duplicate ADD COLUMN errors gracefully; for PostgreSQL, use a DO block or check `information_schema.columns`).
- Alternatively, use the existing Alembic migration infrastructure (`database.py:run_migrations()`) for cleaner versioned migrations.
- Add to the migration helper lists if needed

**2. Pipeline changes** (`backend/pipeline/pre_tier.py`):
- `_predict_with_model()` currently calls `extract_features(hostname)` and builds the feature vector internally, but only returns mission tags
- Modify to also return the feature vector, or create a separate function `extract_pre_tier_features(hostname)` that stores the raw feature dict
- Decision: Add a property `_last_features` or better, refactor to return `(tags_dict, features_dict)`
  - `predict_mission_tags()` still returns the existing API contract
  - New function `extract_pre_tier_features(hostname) -> dict` for the raw 60-dim vector

**3. Ingest changes** (`backend/routers/ingest.py`):
- After calling `pre_tier.predict_mission_tags()`, call `extract_pre_tier_features(hostname)` 
- Serialize features to JSON and store in the insert query

**4. Reference distributions** (`backend/ml/`):
- Create `pre_tier_reference_distributions.json` — computed from training data (synthetic_assets + supplemental hostnames)
- Script: `backend/scripts/compute_pre_tier_reference.py` or extend existing compute script
- Same format as `reference_distributions.json`: per-feature bins + expected proportions

**5. API endpoint** (`backend/routers/queue.py` or new router):
- `GET /api/drift/pre-tier` → reuses `analysis.drift.compute_drift()`
- Response model similar to `MlDriftResponse` with per-feature PSI, composite_psi, status, total_samples
- Use the same reference distribution loading pattern as `get_ml_drift()`

**6. Tests** (`backend/tests/`):
- Unit test: compute_drift with Pre-Tier reference dists
- Integration test: GET /api/drift/pre-tier returns expected structure
- Test empty state, populated state

### Acceptance Criteria
- Pre-Tier feature vectors stored in DB during ingest
- `GET /api/drift/pre-tier` returns valid PSI metrics
- All existing tests pass
- No impact on scoring or pipeline behavior

## Item 4: EPSS Drift Monitoring

**Effort:** 5–6 hrs | **Assignee:** strike | **Priority:** High

> ⚠️ **Effort revised upwards from roadmap's 2-4 hrs.** Critical review identified: 1hr DB migration + 0.5hr pipeline + 0.5hr ingest + 2hr reference script with name mapping + 1hr API + 0.5hr tests = 5-6 hrs.

### What
Add PSI-based drift monitoring for the EPSS fallback models (v4/v3/v2/v1, 37-dim or 22-dim feature vectors). Same pattern as Item 3.

### Why
The EPSS substitution models (v4 → v3 → v2 → v1 → rule engine) adjust raw EPSS scores for sector relevance. If the input feature distribution shifts (e.g., different CWE mix, different agency ratios), the substitution quality degrades.

### Implementation

**1. Database schema** (`backend/database.py`):
- Add `epss_features TEXT` column to `vulnerabilities` table in both SQLite and PostgreSQL
- Add `epss_features TEXT` column to `resolved_vulnerabilities` table
- **⚠️ CRITICAL: Same DB migration issue as Item 3.** Use `ALTER TABLE` statements or Alembic migration. See Item 3 §1 for details.

**2. Pipeline changes** (`backend/ml/epss_substitutor.py`):
- **⚠️ Feature vector is positional list, not named dict.** `_build_feature_vector_v2()` returns `list` (37 elements) and `_build_feature_vector_v1()` returns `list` (22 elements). But `compute_drift()` expects `list[dict]` with `feature_name: value` pairs.
- **Fix:** Convert the positional list to a named dict before storage. Create a position-to-name mapping for v2 (37 names) and v1 (22 names). Store as JSON dict, not JSON array.
- v2 feature names (37): `raw_epss`, `cvss_score`, `exploit_maturity`, `cisa_kev`, `has_public_poc`, `vendor_patch_status`, plus 11 agency OHE names, plus 20 CWE OHE names.
- v1 feature names (22): `raw_epss`, `cvss_score`, `cisa_kev`, plus 8 agency OHE names, plus 11 CWE OHE names.
- **Also handle dimensionality differences:** The active EPSS model version (v4/v3/v2=37-dim, v1=22-dim) determines which features are stored. Store the model version alongside the features. Reference distributions should match the v4 format by default.
- Modify `calculate_substitution()` to optionally include the feature vector in the result dict (backward-compatible, existing callers ignore extra keys).

**3. Ingest changes** (`backend/routers/ingest.py`):
- After `calculate_substitution()`, extract the feature vector from the result
- Serialize to JSON and store in the insert query alongside EPSS fields

**4. Reference distributions** (`backend/ml/`):
- Create `epss_reference_distributions.json`
- Source: computed from training data in `synthetic_findings_v4.json` and EPSS corpus
- Same bin/expected format as existing reference distributions
- Script: `backend/scripts/compute_epss_reference.py`

**5. API endpoint** (`backend/routers/queue.py`):
- `GET /api/drift/epss` → reuses `analysis.drift.compute_drift()`
- Response model similar to `MlDriftResponse`

**6. Tests** (`backend/tests/`):
- Test the stored feature vector extraction
- Integration test for GET /api/drift/epss

### Acceptance Criteria
- EPSS feature vectors stored in DB during ingest
- `GET /api/drift/epss` returns valid PSI metrics
- All existing tests pass
- No impact on scoring or pipeline behavior
