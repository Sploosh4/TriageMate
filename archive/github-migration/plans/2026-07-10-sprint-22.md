## Item 1: Multi-Window KEV Labels

**Effort:** ~6-8 hrs | **Priority:** High | **Core ML improvement**

### What

Replaced binary KEV label (0/1) with 5-class multi-window labels that capture how recently a CVE was added to CISA's Known Exploited Vulnerabilities catalog:

| Label | Window | Meaning |
|-------|--------|---------|
| 0 | Not KEV | CVE is not in the KEV catalog |
| 1 | ≤30 days | Added to KEV within the last 30 days |
| 2 | 31–90 days | Added to KEV 31–90 days ago |
| 3 | 91–365 days | Added to KEV 91–365 days ago |
| 4 | >365 days | Added to KEV more than 365 days ago |

### Implementation

**In `backend/ml/train_xgboost.py`:**
- Changed `construct_labels()` to produce multi-window labels based on KEV addition date
- Switched XGBoost objective from `binary:logistic` to `multi:softprob` with `num_class=5`
- Updated evaluation metric from AUC to multi-class log loss
- Added `window_probabilities` to the training output

**In `backend/ml/xgboost_predictor.py`:**
- Updated predictor to return both `exploitation_probability` (any-KEV probability, sum of windows 1–4) and `window_probabilities` (per-window breakdown) for transparency
- Maintained backward compatibility with Tier 1 routing and scoring engine that reads `exploitation_probability`

### Backward Compatibility

- `exploitation_probability` is preserved as the sum of window probabilities 1–4
- The scoring engine's `ml_exploitation` dimension continues to read `exploitation_probability`
- Tier 1 routing logic unchanged (reads `confidence` and `exploitation_probability`)

### Acceptance Criteria

- [ ] XGBoost trains with `multi:softprob` objective and `num_class=5`
- [ ] Predictor returns `exploitation_probability` (0–1) and `window_probabilities` (list of 5 floats)
- [ ] `exploitation_probability` matches sum of window probabilities 1–4
- [ ] All existing Tier 1 and scoring tests pass without modification
- [ ] Feature count remains 68 total (35 tabular + 33 PCA-reduced SBERT) for XGBoost

## Item 4: Model Registry Rollback API

**Effort:** ~4-5 hrs | **Priority:** Medium | **Operations**

### What

Added a rollback endpoint for the XGBoost model registry, enabling operators to revert to a previous model version when the current model performs poorly.

### Implementation

**In `backend/routers/models.py`:**
- Added `POST /api/models/xgboost/rollback?version=<tag>` endpoint
- Validates the requested version exists in the registry
- Implements lock mechanism to prevent concurrent rollbacks
- Invalidates any cached predictions after rollback
- Returns the new active model version on success

**In `backend/tests/test_rollback.py`:**
- `test_get_versions_returns_list()` — GET returns available versions
- `test_rollback_nonexistent_version()` — Returns 404 for invalid version
- `test_rollback_same_version()` — Returns 400 when rolling back to current version
- `test_rollback_to_previous_version()` — Successful rollback updates active version

### Acceptance Criteria

- [ ] `POST /api/models/xgboost/rollback?version=v2` returns 200 and updates active version
- [ ] `POST /api/models/xgboost/rollback?version=nonexistent` returns 404
- [ ] `POST /api/models/xgboost/rollback?version=v2` (when v2 is current) returns 400
- [ ] Lock mechanism prevents concurrent rollbacks
- [ ] All tests pass
