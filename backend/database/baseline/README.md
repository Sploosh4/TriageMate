# Consolidated database baseline

This package supplies the single current schema definition for explicit pipeline, local UI and prepared-runner setup. `backend.database.installation.setup()` prepares protected credentials and installs the requested profile atomically; subsequent setup verifies the existing installation without resetting evidence or credentials. The central migration registry owns revisions after this baseline. Existing v113 installations require explicit verified adoption with a backup and independent restore proof; routine setup refuses them. The retained development database has completed verified metadata adoption; the retained runner has also completed backup/restore, full attribution, metadata adoption and restricted-login preparation, while the complete Sprint 3 check set passed through native v5 and its formatting-only v6 continuation in [#136](https://github.com/Sploosh4/TriageMate/issues/136). Do not run `schema.sql` manually against an existing database.

`schema.sql` was exported from a fresh isolated PostgreSQL 16 database built through the repository's v113 chain without loading synthetic fixture rows. The construction manifest records the predecessor artifacts and source revision. The final fixture-free database contains only its installation row as stored data; current reference definitions are represented in schema objects. The installation row is deliberately not exported as seed data. No development or lab database supplied these construction artifacts.

`predecessor-contract.json` records the isolated chain's exact catalogue fingerprints. `current-contract.json` records a separate empty database populated with the consolidated schema and the separately captured privileges. Global roles and database/built-in function grants require explicit installation because a schema-only export does not include them. `privileges.json` captures the expected non-owner built-in function grants and database grants; the construction manifest records role attributes. Neither artifact contains passwords.

The initial round trip differs in four deparsed definitions: the `enrichment_source` check and `public_claim_insert` policy flatten nested associative OR expressions; the `current_completeness_cells` and `current_vulnerability_completeness_cells` view rules add generated `AS text` aliases to literals in non-leading UNION branches. All other fingerprint categories match. Preserve separate exact predecessor/current contracts instead of stripping parentheses or aliases from arbitrary SQL during verification. These construction observations do not replace required behavioural and evidence-preservation checks.

`catalogue.fingerprint()` reads definition and effective-authority metadata, including unexpected non-system objects; `require_contract()` rejects missing, extra or changed categories. `evidence.evidence_receipt()` separately hashes every stored non-system relation except installation metadata in a read-only, stable owner-authorized snapshot. Its server-side cursors bound client memory, and canonical output settings keep dates, time zones, intervals and binary values consistent while restoring caller settings. Receipts contain counts and hashes rather than source records. Protected local receipts, attribution verification and an independently verified backup are all required for existing-database adoption.

The ordinary synthetic and prepared-runner profiles require their separate independently constructed contracts before activation; those constructions and fresh-install checks are now complete. Synthetic bootstrap grants the fixture role explicit mutation access to nonempty fixture tables, loads the original 277 rows and adds a synthetic EPSS connection. The prepared runner initializes PostgreSQL and its database as `triagemate`, creates application objects as `tm_mock_owner`, then resets to the provisioning session for initial reader grants. Its built-in ownership/ACL grantors and explicit database-owner connection grant therefore differ from the ordinary local profile. Preserve those source-defined ownership/grant records; do not infer a profile from host names or strip grantor identities to force a match. No runner access or reprovisioning is required to construct these synthetic references.

The recoverable transition has isolated synthetic coverage for archive/receipt creation, restore into another cluster, source-target refusal, archive corruption, row/sequence/metadata preservation and current-baseline repeat installation. Adoption additionally requires unchanged annotations and evidence, a matching restore proof and the caller's full source-attribution verifier. It holds separate write barriers before opening the stable verification snapshot. These mechanisms do not authorize changing an unrecognized profile or replace the required operating steps to drain writers, preserve bundle/workspace manifests, validate replay and retain originals.

Independent ordinary-synthetic and runner predecessor constructions are now captured under `profiles/`. Compared with the empty predecessor, ordinary synthetic changes only `object_acl`; the runner changes `extensions`, `roles`, `object_acl` and `database_acl`. The baseline schema definition remains shared. `synthetic-grants.sql` records the exact final fixture grants, and profile-specific built-in/database grants preserve the measured differences. Fresh-layout contracts retain each profile's authority while accounting for the four previously established deparser changes. Independent fresh installs match both complete contracts and all 277 original fixture records plus the synthetic EPSS connection; isolated profile-specific adoption/restore tests also preserve rows, sequences and installation annotations. The development transition has passed backup/restore, exact evidence preservation and configured-path restart checks. The retained runner also contains archived backend objects in its `public` schema; the independently constructed retained-runner companion verified and preserved those definitions and rows through adoption, without treating its public namespace as empty or resetting it.

`fixtures.json` is the byte-preserved explicitly synthetic original fixture payload. Fresh synthetic setup must load those records before its final authority check. Because the old setup seeded before later builtin hardening and row policies, the consolidated transaction temporarily grants function access and per-seed-table fixture policies to the new non-login, non-member fixture role, loads the fixed records, validates deferred provenance constraints as the installation owner, removes those policies, restores the original function grants and verifies the exact final contract before commit. No temporary seed privilege is published and empty installations do not load records. All setup and verification callers use this single fixture location.

The explicit local `manage.py setup` and retained-runner preparation entry points now delegate to the consolidated installer with their respective `synthetic` and `runner` profiles. Local lifecycle remains explicit; runner preparation still requires the already provisioned cluster/database and exact checkout, database, user and data-directory identity. Neither entry point automatically adopts a v113 installation. Isolated entry-point tests cover complete installation, repeat verification, preserved credentials, drift/version refusal and transactional rollback. The original local schema/fixture/grant helper implementations and the EPSS historical projection dispatcher have been retired. Pipeline consumers use the shared verifier; the completed runner transition and combined complete-check-set evidence are recorded in #136.

The historical v1–v113 Python migration modules and ordered dispatcher have been retired after their consumers moved to the shared verifier. Public Windows reference/provenance records live in `references/`, byte-identical to the source hashes in `construction.json`, and are included individually in the current installation manifest. They remain distinct from the fixture-free SQL definition and its independent complete catalogue/authority contract. The old pipeline/UI SQL definitions and duplicate fixture payload have also been removed. SQL behavior tests call installed functions and views directly; the pre-optimization trigger definition is retained only in `backend/tests/fixtures/validation/` for an independent scan-count comparison. Source-file retirement alone does not establish adoption; use the separate verified transition receipts and canonical acceptance record.

The [retained runner companion](../retained_runner/README.md) adds exact adoption contracts for the archived public revision 058 alongside runner evidence. It preserves all public definitions, rows and legacy authority without changing ordinary fresh installs or previously adopted baseline artifact records. Its additional immutable artifact ledger applies only to that retained layout; it is not a general acceptance path for arbitrary public schemas.
