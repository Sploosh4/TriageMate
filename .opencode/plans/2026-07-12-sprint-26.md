## Background

The graphify `feature_parity.md` reports mismatches between inference (40 tabular) and training (35 tabular). **Deep analysis reveals the 35-feature tabular core IS already consistent** — all three sources (`train_xgboost.py`, `xgboost_predictor.py`, `build_training_corpus.py`) import from the canonical `TABULAR_FEATURE_ORDER` in `pipeline/config/feature_names.py` and produce the same 35 features in the same order.

The "40 tabular" count in graphify is an AST artifact — `build_feature_vector()` in `ingest_helpers.py` returns **46 keys** (35 tabular + 11 metadata/enrichment keys), and graphify counts all dict keys as "tabular."

**However, 3 real bugs remain:**

| # | Bug | Location | Impact |
|---|---|---|---|
| 1 | CIA defaults: `cvss_c/cvss_i/cvss_a` default to **2 (High)** in inference predictor, **0 (None)** in training | `xgboost_predictor.py:240-242` | If caller omits CVSS component fields, model receives wrong values silently |
| 2 | `patch_available` defaults to **True** in inference predictor but training data is ~30% positive | `xgboost_predictor.py:271` | Optimistic bias when data missing |
| 3 | Key name mismatch: `train_xgboost.py` stores `reference_count` in enriched CVEs dict; canonical name is `nvd_reference_count` | `train_xgboost.py:372,694` vs `feature_names.py:34` | Confusing, could cause drift if someone changes one path |

**Additionally:**
- `build_feature_vector()` docstring says "42-key" but returns 46 keys, mentions `osv_lead_days` which doesn't exist
- `reference_count` is systemic — **only** `train_xgboost.py` uses the old key; every other script (`fetch_nvd_corpus.py`, `refresh_caches.py`, `build_training_corpus.py`) already uses the canonical `nvd_reference_count`
- **No mechanical test exists** that would catch future drift in the feature contract
- NPZ already stores `feature_names` (both `train_xgboost.py:save_training_data()` and `build_training_corpus.py` add it), so Issue #6 is done
- **Existing `test_feature_parity.py`** (316 lines, 6 tests) already covers tabular keys, predictor shape, NPZ columns — the new `test_feature_contract.py` should complement, not duplicate

## Phase 1: Fix Existing Discrepancies

**Goal:** Fix the 3 real bugs identified above.

### 1.1 Fix CIA Defaults in `xgboost_predictor.py`

**File:** `backend/ml/xgboost_predictor.py`
**Lines:** 240-242

**Change:** In the `_defaults` dict, change:
```python
"cvss_c": 2,   →   "cvss_c": 0,
"cvss_i": 2,   →   "cvss_i": 0,
"cvss_a": 2,   →   "cvss_a": 0,
```

**Rationale:** Training always parses CVSS vector components and defaults to "N" (None), which maps to 0. The predictor should match this. If the caller provides real CVSS data, the dict `features.get()` will return the real value and the default is irrelevant. This only matters when data is missing — and when data is missing, 0 (None/doesn't apply) is safer than 2 (High).

### 1.2 Fix `patch_available` Default in `xgboost_predictor.py`

**File:** `backend/ml/xgboost_predictor.py`
**Line:** 271

**Change:** In the `_bool_defaults` dict, change:
```python
"patch_available": True,   →   "patch_available": False,
```

**Rationale:** Training data has ~30% `patch_available = True`. Defaulting to True is an optimistic bias. Defaulting to False is neutral (pessimistic, but safer). Most importantly, it matches the pattern of the other `_bool_defaults` where `False` is the fallback.

### 1.3 Fix `reference_count` Key Name in `train_xgboost.py`

**File:** `backend/ml/train_xgboost.py`
**Lines:** 372, 694

**Change:**

Line 372 (was `reference_count`, now `nvd_reference_count`):
```python
"nvd_reference_count": len(cve.get("references", [])),
```

Line 694 (add backward compat for cached enriched_cves.json):
```python
X[i, 23] = cve.get("nvd_reference_count", cve.get("reference_count", 0))
```

**Rationale:** The canonical feature name in `TABULAR_FEATURE_ORDER` is `nvd_reference_count`. Every other script (fetch_nvd_corpus.py, refresh_caches.py, build_training_corpus.py) already uses this name. Only `train_xgboost.py` is out of step. Backward compat is needed because `train_xgboost.py` caches enriched_cves.json to disk — existing cached files will have the old `reference_count` key.

### 1.4 Fix Stale Docstring in `ingest_helpers.py`

**File:** `backend/ingest_helpers.py`
**Line:** ~399

**Change:** Update the `build_feature_vector()` docstring:
- `"42-key feature dict"` → `"46-key feature dict"` (or correct count)
- Remove mention of `osv_lead_days` (doesn't exist in return dict)

## Phase 2: Feature Contract Test

**Goal:** Create a mechanical test that enforces the feature contract and makes future drift impossible.

> **Note on existing coverage:** `backend/tests/test_feature_parity.py` (316 lines, 6 tests) already verifies tabular keys exist in `build_feature_vector()`, predictor array shape, model acceptance, and NPZ column ordering. The new `test_feature_contract.py` fills gaps NOT covered there: canonical registry completeness, functional training-pipeline output shape, and element-by-element default value consistency.

### 2.1 Test File: `backend/tests/test_feature_contract.py`

#### Test 2.1: `test_canonical_registry_is_complete`
```python
def test_canonical_registry_is_complete():
    """The canonical feature registry must have exactly 35 unique names."""
    assert len(TABULAR_FEATURE_ORDER) == 35
    assert len(set(TABULAR_FEATURE_ORDER)) == 35  # no duplicates
```

#### Test 2.2: `test_training_complies_with_registry`
```python
def test_training_complies_with_registry():
    """Training pipeline produces features matching the canonical order."""
    # Extract the feature indices from build_tabular_features() via AST or
    # by running a small test that calls the function and checks names.
    # Strategy: train_xgboost.py imports TABULAR_FEATURE_ORDER and builds
    # features by index. We verify that the import is used correctly by
    # inspecting the file's import and the index assignments.
    #
    # More robust: run build_tabular_features() on 2-3 sample CVEs and
    # assert the returned array shape[1] == 35.
```
**Implementation note:** Rather than brittle AST parsing, we test functionally: call `build_tabular_features()` (or its equivalent) on 2-3 synthetic inputs and verify the output array has 35 columns. Then verify that `save_training_data()` stores `feature_names` matching `TABULAR_FEATURE_ORDER`.

**Easy-to-fix error message:** If this fails, the message says: `"Training pipeline produced {n} features but canonical registry has 35. Run 'python -m scripts.build_training_corpus' after adding/removing features, and update TABULAR_FEATURE_ORDER in pipeline/config/feature_names.py."`

#### Test 2.3: `test_inference_predictor_complies_with_registry`
```python
def test_inference_predictor_complies_with_registry():
    """Inference predictor uses the canonical feature order."""
    # Call _build_tabular_array() with a minimal features dict
    # and verify the output array has 35 columns.
    # Also verify that _build_tabular_array iterates over TABULAR_FEATURE_ORDER
    # (already does — confirmed by code inspection at line 276).
```
**Easy-to-fix error message:** `"Inference predictor produced {n} features but canonical registry has 35. Add/remove entries in _build_tabular_array() to match TABULAR_FEATURE_ORDER in pipeline/config/feature_names.py."`

#### Test 2.4: `test_default_value_consistency`
```python
def test_default_value_consistency():
    """Training and inference default values for shared features must match."""
    # Call _build_tabular_array() with an EMPTY dict — forces all defaults.
    # Call build_tabular_features() on a CVE with NO CVSS vector — forces training defaults.
    # Compare the first 35 values. They should match.
    
    predictor_defaults = _build_tabular_array({})  # all defaults
    # ... compare to training defaults
    
    for i, name in enumerate(TABULAR_FEATURE_ORDER):
        assert predictor_defaults[0, i] == training_defaults[0, i], \
            f"Default mismatch at index {i} ({name}): inference={predictor_defaults[0,i]}, training={training_defaults[0,i]}"
```
**Easy-to-fix error message:** `"Default mismatch at index {i} ({name}): inference={v1}, training={v2}. Update the _defaults or _bool_defaults dict in xgboost_predictor.py to match training behavior in train_xgboost.py."`

#### Test 2.5: `test_npz_columns_match_registry`
```python
def test_npz_columns_match_registry():
    """Saved NPZ training data has feature_names matching the canonical registry."""
    data = np.load("backend/ml/training_data_v2.npz", allow_pickle=True)
    npz_names = list(data["feature_names"][:35])  # first 35 are tabular
    assert npz_names == TABULAR_FEATURE_ORDER, \
        f"NPZ tabular feature names differ from canonical registry.\n" \
        f"In NPZ but not in registry: {set(npz_names) - set(TABULAR_FEATURE_ORDER)}\n" \
        f"In registry but not in NPZ: {set(TABULAR_FEATURE_ORDER) - set(npz_names)}"
```

### 3.3 Wire into GitHub CI

**File:** `.github/workflows/ci.yml`

Add a step in the test job that runs `just check-feature-parity`.

The CI should block on mismatch (exit non-zero) with a clear error message. The error message in the test itself is designed to tell the developer exactly what's wrong and how to fix it (see Phase 2 test messages).

### 3.4 "Easy to Fix" Design

The error messages in the tests are the key to making this easy to fix. Each failure tells you:
1. **What** is wrong (e.g., "Feature X at position 12 differs")
2. **Where** to fix it (e.g., "Update _defaults in xgboost_predictor.py" or "Update TABULAR_FEATURE_ORDER in feature_names.py")
3. **What command** to run after (e.g., "Run 'python -m scripts.build_training_corpus' to rebuild")

This follows the principle: **the error message IS the fix instructions.**

## Appendix: Feature Pipeline Map

### Training Pipeline
```
NVD fetch → enriched_cves.json → build_tabular_features() → X (35 cols)
                                       ↓
                                 SBERT encode → X_text (384 cols)
                                       ↓
                                 np.hstack → X (419 cols)
                                       ↓
                                 save_training_data() → training_data.npz
                                                        + feature_names (419 names)
```

### Inference Pipeline
```
ingest_helpers.build_feature_vector() → features dict (46 keys: 35 tabular + 11 metadata)
                                              ↓
                    xgboost_predictor._build_tabular_array(features) → tabular (35 cols)
                                              ↓
                    xgboost_predictor.predict(features) → X (35 + 384/ PCA cols)
```

### Canonical Registry
```
pipeline/config/feature_names.py → TABULAR_FEATURE_ORDER (35 names)
                                   ↑ Both training and inference import from here
```
