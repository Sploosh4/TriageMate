## Item 1: Product/Security Decisions

**Goal:** Unblock Items 2 and 4 by resolving the two open decisions flagged as "needs product decision" in Sprint 28.

### 1a — Restrict `rag_query` to the finding's hostname?

**Source:** PIPE-HIGH-5 investigation (`backend/reports/investigations/agent-tool-access-boundary.md`)

**Context:** The Tier 2 agent exposes 12 tools. The hostname binding check (in `execute_tool()`) prevents the LLM from querying hostname-scoped tools for hosts other than the case under investigation. However, `rag_query` (#12) accepts `query_text` (not `hostname`), so it bypasses the binding check entirely. The LLM could probe the LanceDB vector store with arbitrary text.

**Options:**

- **A — Accept (status quo):** `rag_query` is the least sensitive read-only tool (returns documentation/patch records). The agent path is feature-flagged off by default. Risk is contained.
- **B — Add hostname binding to `rag_query`:** Either pass the case hostname alongside query_text in the tool definition and add a check, or rename the parameter/use a secondary check. ~15 min effort.
- **C — Both B + remove `execute_tool` from `__init__.py` public API.** ~20 min total.

**Action:** The AI executing this sprint MUST:
1. Present these options to the user with the recommendation
2. Obtain an explicit user decision before implementing an option. Do not infer approval from silence for this security-boundary choice.
3. Document the decision in `docs/architecture/rag-query-access-boundary.md`

### 1b — Is `/api/config` safe to expose without authentication?

**Source:** ROUTER-LOW-1 investigation (`backend/reports/investigations/phase-8-remaining.md`)

**Context:** `GET /api/config` returns pipeline routing thresholds, scoring weights, feature names (68 tabular), and ML threshold info. The endpoint uses `get_current_user_if_enabled` — in dev mode (AUTH_DISABLED) it returns a default admin dict. Feature names + thresholds could theoretically be used to reverse-engineer the ML pipeline.

**Options:**

- **A — Accept current exposure:** Thresholds are operational config, not secrets. Internal tool.
- **B — Gate behind admin-only auth:** Already partially done via `get_current_user_if_enabled`. Make auth mandatory for this endpoint.
- **C — Strip `feature_names` from the response:** The 68 feature names are the most sensitive item as they reveal the ML model's exact input dimensions.

**Action:** The AI executing this sprint MUST:
1. Present these options to the user with the recommendation
2. Obtain an explicit user decision before implementing an option. Do not infer approval from silence for this configuration-exposure choice.
3. Implement the chosen option and document in `docs/architecture/config-api-exposure.md`

### 2c — Seed-Data Idempotency (INFRA-HIGH-2)

**Source:** `backend/reports/investigations/phase-8-remaining.md`

**Problem:** `backend/seed_data.py` uses plain `INSERT` with no UNIQUE constraint on `vulnerability_id` + `hostname`. Running it twice inserts 14 rows instead of 7.

**Fix (Option A — recommended):**
1. Inspect and deduplicate existing `(vulnerability_id, hostname)` duplicates before adding a UNIQUE constraint in a forward Alembic migration.
2. Use a SQLite/PostgreSQL-compatible conflict-safe insert, such as `ON CONFLICT (vulnerability_id, hostname) DO NOTHING` where supported, or a dialect-aware equivalent. Do not use SQLite-only `INSERT OR IGNORE`.
3. Update tests for both supported database backends and any affected seed-data expectations.

**Verification:** Run `python backend/seed_data.py` twice and confirm only 7 rows exist. `just test` passes.

**PR notes:** Requires a new Alembic migration (migration 010). Commit directly to main.

### 2d — OTX Throttling Handling (INT-MED-3)

**Source:** `backend/reports/investigations/phase-8-remaining.md`

**Problem:** `backend/integrations/otx.py` catches 429 (rate-limit) errors in a bare `except Exception` with no retry, backoff, or distinct logging.

**Fix:**
1. Add HTTP 429 detection in the except clause via `resp.status_code`
2. Implement exponential backoff retry (2s, 4s, 8s) with max 3 retries
3. Log a distinct warning for rate-limit events
4. If max retries exceeded, return `{"otx_data": None, "error": "Rate limited after 3 retries"}`

**Verification:** Mock tests for 429 response and verify retry behavior. `just test` passes.

**PR notes:** Single-file change to `backend/integrations/otx.py`. Commit directly to main.

### 2e — Rate-Limit Policy and Implementation (CORE-MED-5)

**Source:** `backend/reports/investigations/phase-8-remaining.md`

**Problem:** Zero rate limiting exists anywhere in the backend. Non-POST routes (GET, PUT, PATCH, DELETE) on sensitive endpoints are unprotected.

**Fix:**
1. Add `slowapi` to `requirements.txt` (or implement a custom middleware if slowapi is too heavyweight)
2. Configure rate limits:
   - POST `/api/ingest`, `/api/ingest/tenable` — highest risk, e.g., 10/minute
   - PUT `/api/admin/config/scoring` — write to config, e.g., 30/minute
   - PATCH `/api/case/{case_id}/notes` — write operation, e.g., 60/minute
   - GET endpoints — lighter limits, e.g., 120/minute
3. Add rate-limit headers to responses (`X-RateLimit-Limit`, `X-RateLimit-Remaining`)
4. Make rate limits configurable via env vars with sensible defaults

**Additional consideration:** The investigation also flagged `ROUTER-LOW-8` (corrupt vs missing threshold file distinction) — this is a very small fix (change `{"status": "unavailable"}` to `{"status": "not_found"}` vs `{"status": "corrupt", "error": "..."}` in `backend/routers/config.py:53-63`). Include this fix as part of the rate-limit PR since it touches the same `routers/config.py` area.

**Verification:** `just test` passes. Test that rate-limited requests return 429.
