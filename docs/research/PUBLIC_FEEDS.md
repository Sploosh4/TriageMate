# Public vulnerability feeds and reusable tools

Research retrieved on 14 October 2026 for the requested open-source, self-hosted refactor. This is a comparison and implementation recommendation, not evidence that any new integration has been installed or accepted. Recommendations assume exactly two running TriageMate containers: the application and PostgreSQL with durable storage. Public enrichment does not establish that an endpoint is vulnerable, that a patch applies, or that remediation occurred.

## Recommended approach

Keep a small number of direct public-source adapters inside the application. Use FIRST's daily EPSS CSV, CISA's KEV JSON, CVE Program records, and selected NVD enrichment. Reuse maintained schema validators and version-specific CVSS implementations where they reduce code. Store source evidence, checkpoints and normalized relationships in PostgreSQL; use a bounded application worker with database coordination rather than adding a message broker or separate ingestion platform. This recommendation is an architectural inference from the source formats and platform requirements below.

The benefit is fewer running services and failure modes. It does not remove the need for pagination, retries, source validation, provenance or careful product/version matching. Keep CVSS, EPSS and KEV separate in the UI; do not silently introduce a combined TriageMate risk score.

## Direct feeds

| Input | Official interface and terms | Version and time semantics | Fit and limitations |
|---|---|---|---|
| FIRST EPSS | Daily gzip CSV at `https://epss.empiricalsecurity.com/epss_scores-current.csv.gz`; FIRST API for small lookups. Free without registration; FIRST requests product/publication attribution. [Data documentation](https://www.first.org/epss/data), [FAQ](https://www.first.org/epss/faq). | Preserve CSV model version and publication/score date; API URL `v1` is its interface version. | CISA KEV | Canonical catalog JSON at `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`; CISA's official GitHub mirror includes schema and history. CC0 data. [Official repository](https://github.com/cisagov/kev-data). | Keep `catalogVersion`, `dateReleased`, per-entry `dateAdded` and `dueDate`; these are different dates. Require declared `count` to match parsed entries. [Official JSON schema](https://github.com/cisagov/kev-data/blob/develop/known_exploited_vulnerabilities_schema.json). | Small, straightforward snapshot adapter. Preserve unknown ransomware status. Membership signals known exploitation; absence does not prove no exploitation. Treat CISA deadlines as source metadata, without applying them as every self-hosting operator's deadline. |
| CVE Program | Official `CVEProject/cvelistV5` records; Git updates or release archives, with daily baselines and hourly deltas relative to a baseline. [Repository and download contract](https://github.com/CVEProject/cvelistV5). CVE reuse is royalty-free under its terms, retaining the copyright designation and licence. [Terms of use](https://www.cve.org/legal/termsofuse). | Retain `dataVersion`, record state, CVE metadata dates, per-provider metadata and immutable commit/archive identity. Validate against the record's declared schema, rather than guessing from its date. [Record schema](https://github.com/CVEProject/cve-schema/blob/main/schema/CVE_Record_Format.json). | Canonical CVE identity/description route. Parse CNA and ADP containers separately. Preserve rejected records and references. A CVE is an identifier; records can contain multiple assessments or no CVSS. A delta requires a known baseline and a recovery path for missed updates. |
| NVD enrichment | NVD CVE API 2.0 at `https://services.nvd.nist.gov/rest/json/cves/2.0`, with developer documentation for querying and synchronization. [CVE API documentation](https://nvd.nist.gov/developers/vulnerabilities), [operating guidance](https://nvd.nist.gov/developers/start-here), [API terms](https://nvd.nist.gov/developers/terms-of-use). NIST-origin material is generally public domain in the US; incorporated CVE material retains its own terms. [NIST licence guidance](https://www.nist.gov/open/license). | Proposed contract: preserve publication/modification fields, response version, metric provider/type/version and query window/checkpoint separately from fetch time. Recheck the current API contract before changing implementation. | Use selected enrichment and bounded incremental fetches. Missing enrichment remains unknown. The NVD developer pages returned an empty/challenge response during this research, so current quotas, date-window limits and exact API-notice wording are not claimed as verified here. |

CVSS is a severity framework with versioned vectors and distinct metric groups. Store the published vector, score, version, assessment source and assessment context together; do not mix base and environment-specific values or silently overwrite conflicting providers. [FIRST CVSS v4 specification](https://www.first.org/cvss/v4.0/specification-document). The [FIRST CVSS v4 calculator](https://github.com/FIRSTdotorg/cvss-v4-calculator) is BSD-2-Clause JavaScript and is a candidate reference implementation for v4 vector validation/recalculation. It does not cover every older version or collect records. Recalculation can detect score/vector inconsistencies; it cannot verify that the underlying assessment is correct.

## Proposed implementation contract

One normalized CVE identity can link many independent observations: provider records, CVSS assessments, daily EPSS scores, KEV snapshots and endpoint findings. Keep each source's identifier, native timestamps, schema/model version, source URL, response identity/hash, retrieval time and import result. Do not make a composite score or one preferred provider a hidden database invariant.

For each adapter, separate download, format/schema validation, normalization and transaction commit. Commit a complete snapshot or completed paginated window atomically; a failed download, invalid body, changed total, missing page or failed insert must leave the last successful evidence and checkpoint intact. Use retry/backoff with provider-specific pacing, enforce TLS and permitted download/redirect origins, and avoid unrestricted URL fetching from source references. Render provider text as untrusted data.

Keep a single bounded collection runner in the application container. PostgreSQL coordination can prevent duplicate collectors and persist due times/checkpoints across app restarts. Keep collection failures visible by source and show last success separately from source publication time. A named PostgreSQL volume survives container replacement, but a backup/restore drill is needed to demonstrate recovery from lost storage.

Before changing ingest code, inspect retained parsers and fixture coverage. The refactor should remove duplication and expensive orchestration while preserving meaningful integrity checks. Add direct regression cases for truncated gzip/JSON, EPSS model changes and zero values, KEV count mismatch and unknown status, CVE rejected records and multi-provider conflicts, paginated interruptions, restart/resume, duplicate replay and source-origin rejection. Use labelled synthetic records and redistributable public samples; private endpoint evidence must not enter the repository.

## Next steps

1. Benchmark the existing active direct adapters with public fixtures: import time, peak memory, database growth, duplicate handling and recovery after interruption. Select one adapter implementation per source.
2. Adopt the daily EPSS snapshot route and preserve model/date metadata; keep small FIRST API lookups optional. Test a historical model-boundary fixture without activating historical bulk backfill.
3. Keep KEV direct. Validate against a pinned schema and tolerate supported additive fields, while preserving the source's version and timestamps.
4. Choose one CVE synchronization mechanism with explicit baseline identity and gap recovery. Prototype go-cve-dictionary only if it demonstrably removes substantial code without dropping provenance or conflicting assessments.
5. Reverify NVD's official developer contract, quotas and attribution requirements when accessible, then confirm incremental window and pagination behavior with public data. An unavailable enrichment provider must not block the rest of the application.
6. Select version-specific CVSS validation code, pin its source and retain licence notices. Test published vectors against trusted reference examples; do not recalculate every score on each page render.
7. Keep Vulnerability-Lookup, OSV, Dependency-Track and DefectDojo as separately scoped candidates. Reopen only the integration that addresses a proven gap; source aggregation and endpoint applicability remain separate concerns.

No new tool was installed, no schedule was activated and no customer/private tenant data was collected for this research. Current licence statements are evidence from the linked upstream sources as retrieved on the research date; recheck the exact pinned release before incorporating code or redistributing source data.
