# Microsoft collection and verification options

Research retrieved on 14 October 2026 for the open-source, self-hosted, two-container refactor. This is a comparison and proposed next experiment, not an installed dependency, tenant assessment or live acceptance result. Only public project code/documentation and existing repository contracts were inspected; no credentials or tenant data were accessed.

## Recommended direction

Use Microsoft's open-source authentication library and a small adapter for the official Graph and Defender APIs inside the application container. Keep PostgreSQL as the second container. This replaces custom authentication machinery without adding a separate collector service, broker or vulnerability-management platform. The recommendation is an architectural inference from the coverage below, not a measured performance claim. [MSAL Python](https://github.com/AzureAD/microsoft-authentication-library-for-python) supports Microsoft identity authentication; its [client-credential documentation](https://learn.microsoft.com/en-us/entra/msal/python/advanced/client-credentials) describes certificates and application secrets.

Evaluate the [Graph Python SDK](https://github.com/microsoftgraph/msgraph-sdk-python) as an alternative to the Graph HTTP adapter, rather than adding both by default. It supplies generated request builders/models and uses Azure Identity credentials, but its own README calls out package size. It does not implement TriageMate's device matching, source history or patch-applicability rules, and Defender's endpoint APIs require their own adapter. Measure install size, import/startup time, retry behaviour and fixture-test complexity before selecting the SDK. Pin whichever route is chosen.

Consider importing versioned Maester results later if tenant configuration checking becomes a product requirement. Maester, ScubaGear and Prowler are posture assessment tools; none of the reviewed evidence establishes complete replacement coverage for the current Entra/Intune/Defender endpoint evidence inventory. Open-source client code also does not remove Microsoft API consent, service licence or sensor prerequisites.

## Current-input coverage

The repository's [Microsoft signal inventory](../planning/MICROSOFT_INFORMATION_INPUTS.csv) defines the current mappings. Five identity/activity signals are already deferred; the refactor should review purpose and evidence value before restoring or deleting them. The table below maps the retained evidence families, rather than claiming that every Microsoft signal is a separate feed.

| Evidence needed | Simplest supported collection route | What still needs verification |
|---|---|---|
| Entra registered device identity/state | Graph v1.0 `GET /devices`; application `Device.Read.All`. [API](https://learn.microsoft.com/en-us/graph/api/device-list?view=graph-rest-1.0) | Preserve directory object ID and shared device registration ID separately; tenant-scope every match. Registration is not proof of endpoint activity. |
| Intune managed device identity, OS and sync | Graph v1.0 `GET /deviceManagement/managedDevices`; application `DeviceManagementManagedDevices.Read.All`; active Intune licence. [API](https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-list?view=graph-rest-1.0) | Preserve Intune ID and `azureADDeviceId`; stale sync or absence is not proof a device is gone. |
| Intune software and explicit software/device relationships | Graph v1.0 `detectedApps` and its documented managed-device relationships. [API](https://learn.microsoft.com/en-us/graph/api/intune-devices-detectedapp-list?view=graph-rest-1.0) | Complete pagination and association collection; detection inventory is not universal local-package coverage or a CVE applicability engine. |
| Intune quality-update policy status | Create/poll/download `reports/exportJobs` for `QualityUpdateDeviceStatusByPolicy`, with required `PolicyId` filter. [Report schema](https://learn.microsoft.com/en-us/intune/device-management/reports/ref-graph-available-reports#qualityupdatedevicestatusbypolicy) | This report supplies policy/device state and timestamps; its documented columns do not prove installation of an exact named KB or identify every device-specific applicable patch. |
| Defender machines and identity | Defender `/api/machines`; retain native ID and nullable `aadDeviceId`. [Resource](https://learn.microsoft.com/en-us/defender-endpoint/api/machine) | Onboarding, licence/RBAC coverage, source last-seen time and ambiguous/duplicate registration IDs. Hostname alone is insufficient. |
| Defender device/software/CVE findings | `/api/vulnerabilities/machinesVulnerabilities`. [API](https://learn.microsoft.com/en-us/defender-endpoint/api/get-all-vulnerabilities-by-machines) | Entitlements, complete response, source software/version and identity binding. A provider finding is an observation, not independent proof of exploitability. |
| Full vulnerability assessment and New/Fixed/Updated changes | `SoftwareVulnerabilitiesByMachine` plus `SoftwareVulnerabilityChangesByMachine`; file export is another supported baseline route. [Export contract](https://learn.microsoft.com/en-us/defender-endpoint/api/get-assessment-software-vulnerabilities) | Persist source history; a delta is not a complete baseline. Preserve the documented time window, composite record identity and checkpoint only after durable import. |
| Missing KB/update advice | `/api/machines/{id}/getmissingkbs`. [API](https://learn.microsoft.com/en-us/defender-endpoint/api/get-missing-kbs-machine) | Report as source-recommended/missing updates; avoid converting a CVE-to-KB relationship into independently verified installation or applicability. |
| Antivirus health | `/api/deviceavinfo`; application `Machine.Read.All`. [API](https://learn.microsoft.com/en-us/defender-endpoint/api/device-health-export-antivirus-health-report-api) | Keep health/scan/refresh clocks separate. This endpoint's documentation warns that token scope can still target the legacy Defender resource even when the request hostname uses the newer API. |
| Recommendations and explicit affected-device relationships | `/api/recommendations` and `/api/recommendations/{id}/machineReferences`; `SecurityRecommendation.Read.All`. [Recommendations](https://learn.microsoft.com/en-us/defender-endpoint/api/get-all-recommendations), [device associations](https://learn.microsoft.com/en-us/defender-endpoint/api/get-recommendation-machines) | Preserve source advice and explicit edges; a recommendation is not authorisation to remediate devices. |

The [export-job creation API](https://learn.microsoft.com/en-us/graph/api/intune-reporting-devicemanagementexportjob-create?view=graph-rest-1.0) currently documents application permissions with `ReadWrite.All`. The [list operation](https://learn.microsoft.com/en-us/graph/api/intune-reporting-devicemanagementexportjob-list?view=graph-rest-1.0) permits read scopes, which does not establish that the creation operation accepts them. A reporting POST can therefore need broad permission even though TriageMate never changes endpoint configuration. Keep export creation isolated to its exact allowed operation, explain that consent clearly, and offer import-only operation when the operator does not grant it. Do not silently request general write permissions for ordinary inventory.

## Collection, validation and independent verification

Collection authenticates and retrieves a provider's observations. Validation checks schema, pagination, record keys, times, provenance and failure handling. Independent verification would establish the underlying endpoint fact using another suitable evidence route. An SDK or posture scanner usually helps the first two; neither automatically supplies the third. A hash checks later byte integrity, not the truth of a provider claim.

Keep a small source envelope containing tenant/source scope, native identifiers, provider observation time when supplied, collection time, collector/schema version, payload digest and complete/failed state. Retain the last complete snapshot on failures. Validate cross-source device bindings explicitly; store unresolved/conflicting bindings instead of hostname-only merges. Preserve source advice, finding presence, patch availability and installed-remediation evidence as distinct facts. This is the recommended TriageMate boundary, derived from the existing evidence contracts rather than imposed by a third-party tool.

The shared HTTP layer should handle cancellation, bounded retries, documented continuation links and provider throttling. Microsoft's [Graph guidance](https://learn.microsoft.com/en-us/graph/throttling) requires reacting to `429` and `Retry-After`; it also states that batched requests are throttled individually. A batch wrapper alone will not solve unreliable collection. Never forward a bearer token to arbitrary continuation or export-download hosts; maintain explicit endpoint/download trust rules and keep temporary download credentials out of logs.

## Proposed next experiment

1. Select one stable source interface: acquire token, collect complete source snapshot, normalize validated rows, commit with provenance. Run it within the application container and store state/checkpoints in PostgreSQL.
2. Compare existing HTTP collection with MSAL plus a small HTTP adapter and with the Graph SDK for Entra and Intune fixtures. Measure startup time, package footprint, request count and cancellation/retry behaviour before replacing the whole connector stack.
3. Exercise synthetic two-page success, `429` recovery, expired credentials, denied scope, foreign-host continuation, malformed payload, duplicate identity, export timeout and restart/replay. Tests must require zero private tenant access and must show failed collection cannot erase the last complete snapshot.
4. Add a Defender baseline/delta fixture pair and prove changes retain device/software/version/CVE identity; verify that a missing record or incomplete export never becomes an inferred Fixed event.
5. Keep posture-tool integration optional. Import a labelled synthetic Maester result only if tenant posture is accepted into scope, retaining check ID, baseline version, run time, outcome and skipped/unknown/error states. Do not install Maester, ScubaGear, Prowler or DefectDojo merely because they mention Microsoft.

No tool adoption, licence change, tenant connection or schedule activation is performed by this research. The project can complete its container/UI refactor while these experiments remain proposals for the next collector decision.
